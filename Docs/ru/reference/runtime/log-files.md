# Лог-файлы среды выполнения и инструментов

Этот справочник перечисляет лог-файлы, которые пишут приложения и инструменты
движка: их имена, расположение, способ открытия, какие из них ротируются и какие
настройки на них влияют. Он также прямо называет то, чего движок не делает
(фильтрация по уровню, ограничения размера, удаление по возрасту), чтобы проект
или оператор мог добавить недостающую политику хранения вне процесса.

Эксплуатационные процедуры, которые используют эти файлы, остаются на страницах
[Эксплуатация релиза](../../how-to/release/operations.md) и
[Отладка](../../troubleshooting/debugging.md).

## Имена файлов и владение

Каждое приложение, которое вызывает `InitApp`, открывает один лог-файл при
запуске, до чтения конфигурации. Имя файла — это имя исполняемого файла без
расширения плюс `.log`. Если путь к исполняемому файлу не удаётся определить,
имя откатывается к `<DevName>.log`, где `<DevName>` — внутреннее имя проекта для
разработки, заданное во время компиляции.

Имя следует за исполняемым файлом на диске, поэтому переименование упакованного
исполняемого файла переименовывает и его лог. При стандартных именах целей
движка файлы такие:

| Процесс | Лог-файл по умолчанию | Открытие | Сохраняется ли предыдущий запуск |
|---|---|---|---|
| Клиент (`<DevName>_Client`, `<DevName>_ClientHeadless`) | `<exe>.log` | Хост переименовывает старый файл, очищает новый, затем runtime-модуль дописывает в него | Один предыдущий запуск в `<exe>.prev.log` |
| Сервер с GUI, без графического интерфейса, демон и служба Windows | `<exe>.log` | Очищается при каждом запуске | Нет |
| Редактор карт Mapper, просмотрщик анимаций, просмотрщик частиц | `<exe>.log` | Очищается при каждом запуске | Нет |
| Сборщик ресурсов, компилятор AngelScript, сборщик Managed-скриптов | `<exe>.log` | Очищается при каждом запуске, строки без меток времени | Нет |
| Предварительная сборка ресурсов внутри процесса сервера или клиента | `<DevName>_BakerLib.log` | Очищается при каждой сборке ресурсов, создаётся относительно рабочего каталога | Нет |
| Исполняемый файл модульных тестов | `<DevName>_UnitTests.log` | Очищается при каждом запуске | Нет |

Связанные файлы, которые не являются логами движка:

- `<exe>_Health.txt` — необязательный файл здоровья сервера, который включает
  `Server.WriteHealthFile`. Он содержит слово состояния, а не текст лога. См.
  [Эксплуатация релиза](../../how-to/release/operations.md).
- `<DevName>_Log_<YYYY.MM.DD>_<HH-MM-SS>.log` пишет кнопка **Save log** в GUI
  сервера. Файл содержит строки, которые в данный момент хранятся в экранном
  буфере, ограниченном `Server.MaxServerLogLines`, и движок никогда его не
  перезаписывает и не удаляет.
- `<exe>.session` — маркер клиентской сессии, описанный ниже.
- `<build-dir>/Testing/<target>-<config>.log` — захваченный консольный вывод
  цели `RunUnitTests`. Это файл дерева сборки, а не лог приложения.

## Куда пишется файл

Каталог — это **корень для записи** (writable root). Корень определяется только
по командной строке и маркеру установщика, поэтому лог может открыться в
окончательном месте до чтения любого файла конфигурации:

1. `--Common.UserWritablePath <path>` в командной строке задаёт корень. Значение
   `*` выбирает каталог данных пользователя.
2. Иначе файл-маркер `INSTALLED` рядом с исполняемым файлом выбирает каталог
   данных пользователя плюс имя проекта.
3. Иначе корень пуст, и лог пишется в **текущий рабочий каталог** процесса.

`Common.UserWritablePath` доступен только для чтения и не может быть задан из
файла конфигурации. Каталоги для каждой ОС описаны на странице [Разделение
клиентской среды выполнения и
обновление](../../explanation/runtime/client-updater.md). Если запрошенный
корень не удаётся создать, процесс записывает в лог предупреждение и пишет
вместо него в рабочий каталог.

Поэтому рабочий каталог важен для автоматических запусков. Менеджер служб, точка
входа контейнера или шаг CI могут запустить процесс из каталога, которого никто
не ожидает. Задавайте рабочий каталог или передавайте
`--Common.UserWritablePath` явно. Лог предварительной сборки ресурсов `BakerLib`
игнорирует корень для записи и всегда создаётся относительно рабочего каталога.

Если лог-файл не удаётся открыть, процесс сообщает `Can't create log file` в
консоль и продолжает работу без файла. Отсутствие лога не является ошибкой
запуска.

### Различия платформ

- **Web:** запись лога в файл отключена. Используйте консоль браузера; см.
  [отладку в браузере](../../how-to/platforms/web-debugging.md).
- **Android:** корень для записи — приватное хранилище приложения, которое
  лаунчер передаёт в командной строке; для отладочной сборки лог —
  `files/<project>.log`. См. [отладку на
  Android](../../how-to/platforms/android-debugging.md).
- **Windows, Linux, macOS:** действуют правила выше. Поведение на macOS для
  этого справочника не наблюдалось.

## Ротация и маркер клиентской сессии

Ротирует свой лог только клиент. Перед открытием нового файла хост клиента
переименовывает существующий `<client>.log` в `<client>.prev.log` в корне для
записи, поэтому лог сбоя или зависания предыдущего запуска остаётся доступным
для чтения после перезапуска. Если другой процесс держит старый файл открытым и
переименование не удаётся, хост пишет предупреждение и продолжает работу;
предыдущий запуск тогда теряется. Сохраняемый файл — ровно один предыдущий
запуск, а не архив. Второй перезапуск перезаписывает его.

Хост держит новый файл открытым всё время запуска, а runtime-модуль клиента
открывает тот же файл в режиме дописывания. Поэтому две половины одного запуска
читаются как один лог. Несколько строк runtime-модуля, записанных до того, как
он инициализирует собственное логирование, попадают только в консоль.

Рядом с логом клиент хранит `<client>.session` — небольшой текстовый маркер,
названный по исполняемому файлу:

- Runtime-модуль записывает его при начале сессии со стадией `Running`, хешем
  сборки, временем запуска и идентичностью процесса.
- Строка стадии переписывается, а не дописывается, по мере продвижения
  завершения работы (выход из главного цикла, остановка клиента, сброс
  приложения, завершение shutdown hook, разрушение глобальных данных, возврат из
  runtime-модуля, запрос выхода). Строка teardown называет разрушаемый набор
  подсистем.
- При следующем запуске маркер читается и удаляется. Если предыдущий процесс не
  дошёл до `ExitRequested` или всё ещё работает, новый запуск пишет в лог
  предупреждение со стадией, набором teardown, сборкой и временем запуска и
  сообщает о нём как о нефатальном исключении. Так различаются сбой, зависание
  при выходе и второй запущенный клиент.
- Маркер, который не удаётся разобрать, потребляется и игнорируется.

Маркер — диагностическое средство. Сохраняйте его вместе с `.prev.log`, когда
собираете свидетельства с клиента, завершившегося аварийно, и не удаляйте его
вручную до следующего запуска.

## Содержимое и формат

- Каждая строка имеет вид `[dd/mm/yy] [hh:mm:ss] <message>`. Сообщения из
  потоков, отличных от главного, добавляют имя потока третьим тегом.
  Инструменты, запущенные с флагом отключения тегов (сборщик ресурсов,
  компилятор AngelScript, сборщик Managed-скриптов), пишут только сообщение.
- Тип сообщения (info, warning, error) **не** записывается в строку. Он
  передаётся только callbacks логирования. Ищите по тексту, а не по префиксу
  уровня.
- Одинаковые последовательные сообщения схлопываются. Перед следующим
  отличающимся сообщением выводится `...and N more same messages`.
- Каждая строка также пишется в стандартный вывод. Поэтому супервизор,
  захватывающий stdout, получает вторую копию лога.
- Фатальные пути и пути аварийного завершения пишут синхронно, включая
  трассировку стека со скриптовыми и нативными кадрами. См.
  [Отладка](../../troubleshooting/debugging.md).
- Переопределения настроек в командной строке, имена которых содержат секретный
  токен (`Common.SecretSettingTokens`), маскируются в логе. Это единственное
  маскирование. См. [Безопасность и
  секреты](../../how-to/release/security-and-secrets.md).

## Уровни и настройки

У движка **нет настройки уровня логирования** и нет фильтра по категориям. Всё,
что записано, сохраняется. На логирование влияют следующие настройки:

| Настройка | Эффект |
|---|---|
| `Common.AsyncLogWrite` | Пишет в файл и консоль из фонового потока. Очередь вмещает не более 100000 сообщений; сверх этого сообщения отбрасываются и записывается уведомление `Dropped N log messages due to high volume`. Фатальные ошибки, проваленные strong assertions и отчёты о сбоях переключают логгер обратно на синхронную запись до вывода отчёта. |
| `Common.NonInteractive` | Диалоги ошибок записывают ошибку в лог и запрашивают завершение с ошибкой вместо ожидания ввода. |
| `Common.SecretSettingTokens` | Подстроки имён, значения которых в командной строке маскируются. |
| `Network.MoveSyncTrace` | Добавляет по одной строке `MOVESYNC` на каждое событие синхронизации движения на сервере и клиенте; слишком многословно для production. |
| `ManagedScript.InteropProbeOnStart` | Добавляет по одной строке `INTEROP-TRANSPORT` на каждый проверенный транспорт при запуске скриптов. |
| `Server.MaxServerLogLines`, `Server.CollapseLogOnStart` | Влияют только на представление лога в GUI сервера и его кнопку **Save log**. |

Текущие значения по умолчанию см. в [справочнике
настроек](../script-api/settings.md). Проекты, которым нужны уровни или
структурированный вывод, подключают собственный приёмник через механизм
callbacks логирования и фильтруют там.

## Хранение: что есть и чего нет

| Поведение | Есть |
|---|---|
| Очистка при запуске (приложения, кроме клиента) | Да |
| Один предыдущий запуск для клиента | Да, `<client>.prev.log` |
| Ротация по размеру | Нет |
| Удаление по возрасту | Нет |
| Сжатие или архивирование | Нет |
| Имена файлов по дням или по запускам | Нет (кроме ручного экспорта из GUI сервера) |

Отсюда два следствия. Перезапуск сервера перезаписывает предыдущий лог сервера,
поэтому свидетельства сбоя теряются, если их не скопировать заранее. Лог долго
работающего сервера растёт без ограничений.

Файл открывается один раз, остаётся открытым всё время жизни процесса, и каждая
запись сначала переходит в конец файла. Поэтому инструмент ротации, который
копирует файл и затем очищает его (copy-then-truncate), продолжает работать, а
ротация переименованием оставляет процесс пишущим в переименованный файл. Это
следует из пути записи в `BaseLogging.cpp`; вывод сделан по исходникам и не
проверялся с конкретным инструментом ротации.

## Рекомендуемая практика проекта

1. **Выбирайте корень осознанно.** Для сервера передавайте
   `--Common.UserWritablePath <writable-root>` и задавайте рабочий каталог
   супервизора в том же месте. Тогда лог, файл здоровья, кеш и база данных
   находятся в одном каталоге, который можно ограничивать по размеру,
   резервировать или очищать как единое целое. Держите его вне неизменяемой
   единицы выпуска, чтобы откат не уничтожал логи.
2. **Архивируйте перед перезапуском.** Скрипт развёртывания или супервизор
   должен копировать `<exe>.log` под имя с меткой времени перед остановкой или
   перезапуском сервера, а затем хранить ограниченное число копий. Если
   развёртывание не удалось, сохраните лог вместе с идентичностью выпуска;
   [Эксплуатация релиза](../../how-to/release/operations.md) требует сохранять
   логи до замены свидетельств.
3. **Ротируйте снаружи.** Для долго работающего сервера используйте ротацию
   copy-then-truncate с ограничениями размера и возраста, которые выбирает
   проект. Движок их не применяет.
4. **Собирайте свидетельства клиента набором.** `<client>.log`,
   `<client>.prev.log` и `<client>.session` вместе объясняют сбой или зависание
   при выходе.
5. **Игнорируйте сгенерированные логи в системе контроля версий.** Логи,
   записанные в рабочий каталог, могут оказаться в корне репозитория, особенно
   после запусков модульных тестов и предварительной сборки ресурсов.

```text
# Engine runtime and tool logs
*.log
*.prev.log
*.session
*_Health.txt
```

Сузьте шаблоны, если проект отслеживает другие файлы `.log`.

6. **Считайте логи конфиденциальными.** Production-логи и вложения со сбоями
   требуют независимой проверки на маскирование данных; движок маскирует только
   случай переопределения в командной строке. Не загружайте весь корень для
   записи как артефакт CI; собирайте именованные файлы. См. [Границы доверия
   CI](../../how-to/release/security-and-secrets.md#границы-доверия-ci) и
   [Настройка непрерывной интеграции для игрового
   проекта](../../how-to/project/continuous-integration.md).

## Логи модульных тестов

Исполняемый файл модульных тестов — обычное приложение движка и, как любое
другое, пишет `<DevName>_UnitTests.log` относительно своего рабочего каталога.
Цель `RunUnitTests` запускает его с каталогом исходников проекта в качестве
рабочего каталога и пишет вывод процесса в
`<build-dir>/Testing/<target>-<config>.log`; при неудачном запуске этот вывод
повторяется в консоли сборки. Сохраняйте лог из дерева сборки как свидетельство
CI и игнорируйте файл в рабочем каталоге. См.
[Тестирование](../../contributing/testing/index.md).

## Контрольный список проверки

1. Лог каждого развёрнутого процесса появляется в предусмотренном корне для
   записи, а не в неожиданном рабочем каталоге.
2. Процедура перезапуска сервера копирует предыдущий лог до того, как новый
   процесс его очистит.
3. Клиент, запущенный дважды, оставляет в `<client>.prev.log` первый запуск.
4. Принудительное завершение клиента приводит к предупреждению о сессии при
   следующем запуске.
5. Политика хранения, включая ограничения и того, кто их применяет, записана
   проектом, потому что движок не применяет никаких ограничений.
6. Сгенерированные логи игнорируются системой контроля версий и исключены из
   пакетов выпуска.
