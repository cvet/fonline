# Необязательная многопоточность клиента

## Проверенные пути исходного кода

- `Source/Client/WorkScheduler.h` и `Source/Client/WorkScheduler.cpp`
- `Source/Client/Client.cpp`, `SpriteManager.cpp`, `ModelSprites.cpp` и `ModelInstance.cpp`
- `Source/Common/Settings.inc`
- `Source/Tests/Test_WorkScheduler.cpp`, `Test_ModelAnimationPoseProcedural.cpp` и `Test_ClientEngine.cpp`

## Назначение

Многопоточность клиента — параметр запуска, а не сборки. Один бинарник поддерживает оба режима: `Client.Multithreading=False` оставляет работу на потоке приложения, `True` разрешает движку запустить дополнительные CPU-потоки. Число потоков движок выбирает по машине при создании клиента. Настройки фиксированного числа потоков, макроса `FO_ENABLE_CLIENT_MULTITHREADING` и отдельного артефакта нет: оба режима должны сравниваться на одной машине с одинаковыми ресурсами.

Реализованы [WorkScheduler](../../../../Source/Client/WorkScheduler.h) с ограниченными синхронными пакетами и постоянными потоками каждого `ClientEngine`, разделение обновления спрайтов в [SpriteManager](../../../../Source/Client/SpriteManager.cpp) и фазы prepare / evaluate / finalize в [ModelInstance](../../../../Source/Client/ModelInstance.cpp). Вычисление анимационной позы модели — пока единственная работа workers.

Render thread, запись GPU-команд вне потока приложения, конкурентные скрипты, параллельные свет, туман и частицы, асинхронная загрузка ресурсов и многопоточный Web не реализованы и не обещаются этим параметром.

Ускорение не заявлено: необходимые сравнения времени кадра ещё предстоит собрать. Тесты установили идентичность поз и обход параллельной подготовки в последовательном режиме. Прежние проверки встраиваемого проекта сообщали одинаковые вердикты игроковых маршрутов в обоих режимах; они не подтверждают каждую последующую ревизию движка и платформу.

## Контракт выполнения

Поток приложения единолично владеет клиентскими сущностями, скриптами, вводом, рендерером, менеджерами спрайтов и атласов и публикацией ресурсов. Worker выполняет только CPU-вычисление над состоянием собственного элемента пакета и неизменными данными, время жизни которых владелец закрепил до окончания пакета.

```text
flowchart LR
    A[Owner: network, input, scripts, map update] --> B[Eligible stage]
    B -->|no workers| S[Direct: the owner calls the kernel itself]
    B -->|workers started| P[Owner prepares a bounded batch]
    P --> W[Workers + owner run the kernels]
    W --> J[Batch drains, first failure is kept]
    S --> C[Owner: apply results, effects, callbacks]
    J --> C
    C --> R[Owner: GPU submission, present]
```

Worker получает заимствования только через индекс собственного элемента. Захватывать клиента, сущность, менеджер или рендерер и обращаться к ним нельзя; `const` в сигнатуре этого не разрешает. Пока пакет выполняется, владелец ничего не публикует: синхронный `RunBatch` возвращает управление лишь после завершения всех элементов.

Вне `RunBatch` незавершённой работы нет, поэтому деструктору scheduler достаточно присоединить простаивающие workers. Отдельная последовательность закрытия приёма, отмены и drain не нужна. Пакет не переживает свою стадию и не подходит для работы между кадрами: будущему пути ресурсов потребуются собственные ограниченная очередь и поколения запросов.

## Планировщик

`ClientEngine::WorkSched` передаётся `SpriteManager` при создании. У каждого встроенного клиента собственные потоки, состояние ошибок и управление работой.

```cpp
if (scheduler->ShouldRunParallel(item_count, min_items)) {
    scheduler->RunBatch("StageName", item_count, 1, [&](size_t index) { RunKernel(items[index]); });
}
else {
    for (auto& item : items) {
        RunKernel(item);
    }
}
```

Стадия выбирает режим только в этой точке. `ShouldRunParallel` возвращает false для последовательного клиента, недостаточного числа элементов и единственного элемента. Последовательная ветка — обычный цикл без job, future, счётчика завершения и временного буфера.

- Число крупных chunks не превышает число участвующих потоков; их размер не меньше `min_items_per_chunk`. Цена планирования зависит от числа потоков, а не элементов.
- Владелец участвует в вычислениях и может обработать весь пакет, если workers заняты или медленно просыпаются. Ни один chunk не остаётся невостребованным.
- Следующий пакет открывается после закрытия предыдущего. Workers копируют его дескриптор под mutex и учитываются до освобождения; `RunBatch` ждёт обнуления этого счётчика. Иначе поздно проснувшийся worker мог бы применить старое вычисление к индексу нового пакета.
- Первая `std::exception` сохраняется, оставшиеся chunks заканчиваются досрочно, а владелец повторно выбрасывает исключение из `RunBatch`. Неудачный элемент не перезапускается молча на основном потоке. `catch (...)` вызывает `FO_UNKNOWN_EXCEPTION()` и завершение процесса согласно [контракту исключений](../../contributing/coding-contracts/exception-safety.md), §2.1.
- Вложенная отправка пакета запрещена и выбрасывает исключение вместо deadlock на занятом ею же пуле.

## Число потоков

`WorkScheduler::ChooseWorkerCount` вызывается при создании клиента. `ReadWorkerCountInputs` сообщает число логических ядер, поддержку потоков и мобильную платформу. Правила применяются последовательно:

| Правило | Причина |
|---|---|
| Нет поддержки потоков, как в Web, — 0 workers | Сборка браузера не использует `-pthread`; общий config может включать параметр, а клиент всё равно работает последовательно. |
| Число ядер неизвестно — 0 workers | Последовательный режим не создаёт избыточной конкуренции на неизвестной машине. |
| Одно ядро оставляется потоку приложения | Он сам вычисляет chunks, поэтому нельзя учитывать его ещё и как отдельного worker. |
| Начиная с `Client.MultithreadingHeadroomMinCores` (4), оставляется ещё одно ядро | Драйвер, микшер и managed runtime имеют свои потоки. При меньшем числе ядер дополнительное ядро полезнее вычислениям пакета. |
| Мобильный предел `Client.MultithreadingMaxMobileWorkers` (2) | Быстрые и медленные ядра работают в тепловом бюджете. Chunks выдаются динамически, но равного размера; медленное ядро задерживает весь пакет. Этот предел только понижает общий. |
| Общий предел `Client.MultithreadingMaxWorkers` (8) | При большем числе workers нынешний пакет поз дробится до одной-двух поз на chunk, и пробуждение с join перестают окупаться. |

Значения по умолчанию дают 0 workers для 1 ядра, 1 для 2, 2 для 3 и 4, 4 для 6, 6 для 8 и 8 начиная с 10; телефон получает не более 2. Нулевой результат допустим и при включённом параметре. Журнал сообщает фактически выбранное число и ограничение: `Client multithreading: on, 6 worker threads (8 logical cores, one core kept for the application thread and one for driver, audio and runtime)`, `Client multithreading: on, running serial (1 logical cores, no core is left over beside the application thread)` или `Client multithreading: off`.

Три порога пока выбраны рассуждением и подлежат настройке по профилю. Их можно менять для captures без пересборки. Они задают правило, а не ответ для конкретной машины. Предел может быть 0: мобильный 0 оставляет телефоны последовательными при параллельном desktop. Пределы обязаны находиться в `0..MAX_WORKER_THREADS` (64), а порог ядер не может быть отрицательным; проверка действует на каждой платформе. Минимальный размер chunk выбирает стадия, а `ShouldRunParallel` оставляет слишком маленький пакет владельцу.

## Первая стадия: CPU-обновление спрайтов

`SpriteManager::BeginScene` сначала материализует `_updateSprites` в vector. Это также устраняет опасность изменения и rehash контейнера, если `Update()` запускает обновление другого спрайта. Только параллельный клиент выполняет подготовку всех элементов до вычисления:

1. Владелец вызывает `Sprite::PrepareUpdate()`, фиксирует работу кадра и всё, чего worker касаться не должен. True означает готовность CPU-работы.
2. `Sprite::RunPreparedUpdate()` вычисляет собственное состояние элемента на worker.
3. Владелец вызывает `Sprite::Update()`, снова имея доступ к GPU и общим менеджерам.

Последовательный клиент обходится исходным однопроходным `Update()`, включая его предикат. Подготовка заранее меняет порядок: продвижение timeline модели может повторно разрешить движение и вызвать animation-init в скриптах, которые меняют другого critter. При пакетной подготовке уже подготовленная модель сохраняет входы и увидит такое изменение на кадр позже. Размер joint masks фиксируется при создании, а live set держит все спрайты через `shared_ptr` до конца обновления; висячих данных нет. Порядок unordered map изначально не был детерминированным. Тем не менее это различие поведения требует визуального сравнения режимов.

### Позы анимации моделей

Пока фазы реализует только `ModelSprite`; `PoseSpriteFrame` вызывает три фазы подряд:

| Фаза | Поток | Работа |
|---|---|---|
| `PrepareSpriteFramePose` | Владелец | Преобразование корня, поворот тела, timeline с возможным animation-init, входы tracks и joint masks контроллеров, процедурные повороты, положение земли по иерархии. Рекурсивно. |
| `EvaluateFramePose` | Worker | `ModelAnimationRuntimePose::Evaluate` каждого узла, world matrices, overrides связанных joints и parent matrix дочерних узлов. Читает собственные буферы и неизменный rig. Рекурсивно. |
| `FinalizeFramePose` | Владелец | Сначала дети, затем настройка и обновление прикреплённых частиц, обновление configuration layout и animation callbacks. Рекурсивно. |

Вся иерархия — один элемент пакета: ребёнок читает только что вычисленный joint родителя. Разделение по узлам потребовало бы барьер на каждом уровне при небольшой глубине иерархий.

Ozz пишет в буферы конкретной pose: sampling contexts, track locals, joint weights и model matrices. Skeleton и clips общие и неизменные. Ozz allocator устанавливается до создания поз и передаёт выделения thread-safe `safe_alloc`.

Первый проход подбора размера кадра в `ModelSpriteFactory::DrawModelToAtlas` потребляет и завершает подготовленную позу. Дополнительные позы для сходимости размера остаются последовательными внутри GPU-стадии и редки после прогрева. Подготовленная поза сохраняет исходный кадр: повторная предварительная подгонка сдвинула бы корень уже вычисленного skeleton. `Render.ModelDirectDraw`, GUI previews и `Prewarm` используют однопроходный путь: они вычисляют позу по требованию во время рисования, без границы пакета.

## Что остаётся у владельца

| Область | Причина |
|---|---|
| `MapView::Process`, `CritterHexView::Process` | Изменяют сущности, поля карты и списки удаления. |
| `MapView::DrawMap` | Перестраивает данные карты, вызывает скрипты между стадиями и записывает GPU-команды. |
| Свет и туман | `ApplyLightFan` меняет общую карту; `FogShape::Input` трассирует живое состояние через callback. Нужны чистое вычисление и неизменный снимок препятствий, без затрат на его создание в последовательном режиме. |
| Частицы | SPARK и Effekseer делят менеджеры, random state и resource callbacks. Потоки middleware и workers клиента должны учитываться в общем CPU-бюджете. |
| Сеть | Stream decompression хранит состояние и порядок, handlers меняют сущности. Нужна упорядоченная передача bytes, а не parallel loop. |
| Подготовка ресурсов | `ReadSpriteResource` подходит для CPU, но публикация меняет cache, atlas и GPU. Нужен отдельный межкадровый путь с поколениями запросов. |
| Скрипты, рендерер, GPU | По контракту имеют одного владельца. Конкурентные C# callbacks и render thread вне этой функции. Маска попадания модели уже приходит через [неблокирующее чтение текстуры](../rendering/index.md#reading-a-texture-back), поэтому picking не создаёт прежнюю синхронную остановку будущего render thread. |

SDL требует основной поток для [SDL_PollEvent](https://wiki.libsdl.org/SDL3/SDL_PollEvent) и [SDL_GL_MakeCurrent](https://wiki.libsdl.org/SDL3/SDL_GL_MakeCurrent); переносимый renderer остаётся там независимо от CPU workers.

## Платформы

| Цель | Состояние |
|---|---|
| Windows, Linux | Оба режима доступны; первые целевые платформы проверки. |
| macOS, Android, iOS | Scheduler общий и режимы предусмотрены сборкой, но проверка не выполнена; параллельный режим нельзя рекламировать как подтверждённый. Android и iOS применяют мобильный предел. |
| Web | Только последовательный режим: правило даёт 0 и сообщает это в журнале даже при включённом параметре. Emscripten не включает `-pthread`, у browser Mono свои правила initialization и main-thread attachment. См. [Web](../../how-to/platforms/web-debugging.md) и [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html). Многопоточный Web требует отдельного артефакта, COOP/COEP и выбора loader; блокировать browser main thread ожиданием worker нельзя, нужна неблокирующая оркестрация. |
| Mapper | Всегда последовательно, независимо от параметра. |

## Измерение

Сравниваются четыре варианта с одинаковыми ресурсами, настройками, renderer, оптимизацией и workload:

| Вариант | Назначение |
|---|---|
| A: ревизия до функции | Найти цену разделения общих вычислений. |
| B: текущая ревизия, `Multithreading = False` | Сравнить последовательный путь с A. |
| C: текущая ревизия, `Multithreading = True`, малая сцена | Цена scheduler без полезного распараллеливания. |
| D: текущая ревизия, `Multithreading = True`, плотная сцена | Масштабирование и выгодное число workers. Повторы с пониженным `Client.MultithreadingMaxWorkers` определяют новые defaults. |

Измеряются median/p95/p99 времени кадра, CPU critical path, GPU time, подготовка пакета и join wait, выделения после прогрева, RSS и input-to-present latency. Нужны режимы с ограничением кадра и без него, а также машина с малым числом ядер. Средний FPS ничего не доказывает.

`SpriteManager::UpdateSprites` и `PrepareSpriteCpuUpdates` (`Render`) обрамляют стадию; `WorkScheduler::RunBatch` (`Threading`) включает join; `WorkScheduler::RunClaimedChunks` каждого участника содержит `ModelInstance::EvaluateAnimationPose` (`Model`). Join владельца — время `RunBatch` вне его `RunClaimedChunks`.

Предлагаемые пороги до принятия режима: A→B не хуже 1% median CPU frame time и 2% p95/p99, с достаточным числом повторов; для D — воспроизводимый выигрыш полного кадра на объявленном workload, без дополнительного буферизованного кадра и существенного ухудшения малых сцен. Предел выгоды задаёт последовательный остаток: `T ≈ T_serial + T_parallel / P + T_prepare + T_join`. Ускорение вычисления не гарантирует такое же ускорение кадра при преобладании GPU или скриптов.

Структурные требования действуют уже сейчас: последовательный путь обходится без добавленной подготовки, workers не трогают состояние владельца, объём работы ограничен, после teardown задач нет.

## Тесты

Скрытый эксперимент `ClientPoseBatchCost` сравнивает одинаковые запечённые анимационные входы, чередуя порядок прямого и пакетного расчёта и точно проверяя матрицы. Его [контракт native-входов](../../../../Source/Tests/README.ru.md#отдельное-измерение-стоимости-пакета-поз) отделяет стоимость ядра от изменчивости сцены; проверки кадра и картинки остаются необходимыми.

- [Test_WorkScheduler.cpp](../../../../Source/Tests/Test_WorkScheduler.cpp) проверяет все правила выбора workers, нулевые и мобильные пределы, отказ на неверном диапазоне, sweep `0..256` ядер с монотонным числом workers и сохранением ядра владельца, платформенные входы, последовательный путь, однократное выполнение элементов и разделение повторных пакетов. Проверены пустой и одиночный пакеты, minimum chunk, parallel threshold, передача ошибок и дальнейшая пригодность scheduler, запрет nesting, shutdown, два независимых scheduler и равенство результатов. `ClientMultithreadingFollowsTheSetting` создаёт реальный client engine, проверяет оба режима, выбранное на этой машине число workers, пониженный предел и выполнение кадров. `ClientSpriteUpdatePhasesFollowTheClientMode` записывает порядок: последовательный клиент вызывает только `Update()`, параллельный готовит всё до evaluate и завершает после drain. Удаление serial guard ломало этот тест при проверке его чувствительности.
- [Test_ModelAnimationPoseProcedural.cpp](../../../../Source/Tests/Test_ModelAnimationPoseProcedural.cpp): `ModelAnimationRuntimePosesEvaluateIdenticallyOnClientWorkers` повторно вычисляет отдельные позы общего rig реальными workers и сравнивает world matrices побитно с последовательным результатом. Эта проверка доступна во всех конфигурациях.
- [Test_ClientEngine.cpp](../../../../Source/Tests/Test_ClientEngine.cpp): `ModelPosePhasesMatchTheSinglePassPose` сравнивает фазы `ModelInstance`, чередуемые как пакет и выполняемые scheduler, с однопроходной позой. Файл требует AngelScript из-за baked-model fixtures; предыдущий тест от этого ограничения не зависит.

Где доступно, запускать native-тесты под ThreadSanitizer и применять [Thread Safety Analysis](../../contributing/coding-contracts/thread-safety-analysis.md). Они отдельно не доказывают lifetime, исключительное владение и порядок callbacks. Headless-тесты не подтверждают визуальную идентичность: реальный renderer надо проверить по анимации, attachments, shadows, particles, bounds, hit testing, переходам карт и GUI previews. Игроковый маршрут встраиваемого проекта проходит дважды, по одному разу в каждом режиме, с сопоставлением вердиктов.

## Дальнейшая работа

1. Профиль четырёх вариантов на первых целевых платформах; последующие стадии выбираются по нему.
2. Вторая стадия, вероятно lighting geometry: сначала чистое вычисление и неизменный снимок препятствий.
3. Отдельный ограниченный prepare/publish ресурсов с поколениями запросов; оценка по latency загрузки и stalls, а не steady FPS.
4. Проверка macOS и Android и решение о многопоточном Web с отдельным loader и isolation.
