# Выбор представления игровых данных
<!-- docs-translation: {"document_id":"choosing-a-data-representation","locale":"ru","source_path":"Docs/en/explanation/entity-and-property-model/choosing-a-representation.md","source_sha256":"b4661a25bdbb64a6ed1fadf55718d28d028a97b84c0e029e17406f83d120365a"} -->
Engine предлагает несколько способов придать игровому понятию форму: стартовая
настройка (setting), строка каталога FixedType, свойство или компонент
прототипа, запись RefType, раскладка ValueType или полноценная сущность. Они
различаются тем, кто может менять данные, сохраняются ли они, доходят ли до
клиентов, есть ли у них идентичность и во что обходится последующее изменение.
Эта страница — руководство по выбору одного из них до написания первого
объявления; синтаксис описывает справочник по метаданным.

## Варианты с первого взгляда

| Потребность | Представление | Объявляется через |
| --- | --- | --- |
| Настраиваемый скаляр, неизменный в течение запуска сервера или клиента | Setting | `///@ Setting <Side> <type> Group.Name` плюс значение в `.fomain` |
| Таблица авторских строк, на которые скрипты и другие данные ссылаются по ID | FixedType | `///@ FixedType <Side> Name`, поля `///@ Property`, строки в файле-контейнере прототипов |
| Значение по умолчанию или возможность вида сущности | Свойство прототипа или компонент свойств | `///@ Property <Entity> ...`, при необходимости с `Component`, создаётся в `[Proto<Entity>]` |
| Состояние отдельной сущности, которое меняется и может сохраняться | Изменяемое свойство | `///@ Property <Entity> <Side> <type> Name Mutable [Persistent] [sync flag]` |
| Структурированное значение, меняющееся целиком и не имеющее идентичности | RefType, хранимый свойством | `///@ RefType <Side> Name` плюс поля `///@ Property Name ...` |
| Небольшое значение фиксированного размера, копируемое как байты | ValueType | `///@ ValueType <Side> Name Layout = type - Field + ...` |
| Native-двойник такого значения | `ExportValueType` | `///@ ExportValueType Layout = ...` на структуре C++ |
| Объект со своим ID, временем жизни, событиями или членством в holder | Entity | `///@ Entity <Side> Name [flags]` плюс `///@ EntityHolder` |

`<Side>` — это `Common`, `Server` или `Client` в зависимости от объявления;
baker отклоняет неприменимую цель (например, `Mapper` у RefType или у
свойства). Точную грамматику читайте в [справочнике по
метаданным](../../reference/metadata/index.md) и в перечисленных выше тестах
baker, прежде чем полагаться на сочетание флагов.

## Последствия каждого выбора

### Setting

- **Сохранение:** нет. Значение читается из авторской конфигурации при запуске,
  а `MetadataBaker` отклоняет объявление, значение которого отсутствует в
  конфигурации.
- **Репликация:** во время выполнения нет. Каждая сторона читает значение из
  своего запечённого профиля; запись метаданных несёт только имя и тип, а движок
  никогда не применяет значения из метаданных.
- **Изменяемость:** встроенные настройки доступны только для чтения после
  стартового снимка. Управляемые свойства `Settings.Group.Name` имеют только
  getter; пользовательские настройки AngelScript сохраняют getter и setter, а
  `SetRuntimeSetting` по-прежнему принимает объявленные проектом настройки.
  Всё равно считайте каждую объявленную настройку конфигурацией; живое состояние
  принадлежит сущности, свойству или владеющему сервису среды выполнения.
- **Идентичность:** ключ с точкой `Group.Name`. Baker отклоняет объявление без
  группы. Парсер конфигурации считает неизвестное имя с точкой пользовательской
  настройкой проекта, поэтому опечатка во встроенном ключе может выглядеть
  допустимой; покрывайте каждую важную настройку точечным тестом, как советует
  [руководство по конфигурации проекта](../../how-to/build/project-configuration.md).
- **Миграция:** вида правила миграции для настроек нет. Переименование —
  согласованное изменение объявления и каждой конфигурации, которая её задаёт.

### Строка каталога FixedType

- **Сохранение:** нет. Строки запекаются в пофронтовый вывод прототипов пакета и
  пересобираются следующим bake, а не читаются из базы данных.
- **Репликация:** во время выполнения нет. `<Side>` типа и каждого поля решает,
  какие запечённые выводы его содержат. Поле только для сервера пропускается в
  клиентском выводе.
- **Изменяемость:** авторские константы. Изменяемое непостоянное (временное)
  свойство не загружается из текста прототипа, поэтому строки несут только
  авторские значения.
- **Идентичность:** `$Name` (или имя файла), уникальное для типа, хешируется в
  `hstring`, не содержит `/`, `$` и пробельных символов. Ссылки на строку из
  других свойств должны называть существующую строку или быть пустыми в
  nullable-свойстве. Наследование `$Parent` работает внутри одного типа.
- **Миграция:** ссылки разрешаются через правила `MigrationRule Proto ...`,
  поэтому переименование или удаление ID строки — это изменение совместимости, а
  не перемещение файла.
- **Доступ:** оба backend генерируют `Game.Get<Name>(id)` и `Game.Check<Name>(id)`
  для каждого FixedType; getter выбрасывает исключение для неизвестного ID,
  поэтому проверяйте через check только тогда, когда отсутствие законно.
- **Авторский файл:** расширение контейнера берётся из `Baking.ProtoFileExtensions`
  (по умолчанию `fopro`). Собственный фикстур использования ресурсов в Engine
  задаёт `fopro foinfo` и создаёт строки в файле `.foinfo`. Baker движка также
  записывают запечённые выводы `.foinfo` (индексы спрайтов и анимаций моделей);
  это не авторские каталоги.

### Свойство прототипа и компонент свойств

- **Сохранение:** неизменяемое свойство живёт в прототипе и не сохраняется для
  каждой сущности. Свойство, сохраняемое вместе с сущностью, должно быть
  `Mutable` и `Persistent`; baker отклоняет `Persistent` без `Mutable`, у
  свойства только для клиента или у виртуального свойства.
- **Репликация:** по свойствам. Изменяемому свойству `Common` нужен тип
  синхронизации (`PublicSync` или `OwnerSync`, либо `NoSync`); свойство,
  изменяемое клиентом, должно синхронизироваться. Неизменяемые значения `Common`
  и значения `NoSync` не передаются в начальных снимках, поэтому общая структура
  должна приходить из прототипа.
- **Изменяемость:** неизменяемое (авторское), изменяемое и сохраняемое либо
  изменяемое и временное (только во время выполнения).
- **Идентичность:** принадлежит владеющей сущности. Компонент её не добавляет: он
  группирует квалифицированные поля (`Bulletin.Region`) под обычным bool-маркером
  у того же владельца, без дополнительной сущности, holder или хранилища.
- **Миграция:** сохраняемое изменение имени требует
  `MigrationRule Property <Owner> Rename`; удалённое имя — `Remove`; перенос
  плоских полей в компонент — это переименование в квалифицированное имя плюс
  тест совместимости сохранений. См. [Формат
  прототипов](../../how-to/content/prototype-format.md#компоненты-свойств).

### RefType

- **Сохранение:** определяется свойством, которое хранит значение. Значение
  записывается целиком, поэтому удаление поля вступает в силу при следующем
  сохранении этого значения.
- **Репликация:** определяется флагами синхронизации хранящего свойства. Сами
  поля RefType не принимают никаких флагов, кроме `Component`.
- **Изменяемость:** чтение возвращает отсоединённую копию (документировано для
  Managed C#; getter AngelScript также копируют необработанные данные свойства
  перед преобразованием). Чтобы изменить поле, прочитайте значение, отредактируйте
  копию и присвойте её обратно свойству.
- **Идентичность:** нет. У RefType нет ID, holder, событий и блокировки. Ему
  нужно хотя бы одно поле, а его поля типа сущности могут быть только
  фиксированными ссылками или ссылками на прототип.
- **Миграция:** переименования и удаления полей используют правила миграции
  свойств, а старые поля пропускаются при чтении сохранённого значения.

### ValueType и `ExportValueType`

- **Сохранение и репликация:** как у свойства, использующего тип; значение
  копируется как байты.
- **Изменяемость:** значение, копируется при присваивании.
- **Идентичность:** нет. Каждое поле должно быть примитивом, enum, `hstring` или
  value-типом с одним полем, смещения должны быть кратны размеру поля, а в конце
  итогового размера не должно быть хвостового выравнивания. Строки, коллекции,
  вложенные записи из нескольких полей и данные с идентичностью не подходят.
- **Миграция:** раскладка входит в контракт метаданных и меняет версию
  метаданных, поэтому сервер и клиенты должны быть из одного bake. Engine не
  документирует миграцию раскладки на месте; планируйте изменение как новый тип
  или свойство плюс миграцию старого.
- **Native-двойник:** `ExportValueType` помечает структуру C++, раскладка которой
  отражена в скриптах; native-тип должен быть тривиально копируемым и иметь тот
  же размер. Для данных только для скриптов используйте `///@ ValueType`.

### Entity

- **Сохранение:** через записи holder. Запись `Persistent` хранит дочерние
  сущности постоянных holder или `Game`; остальные записи временные.
- **Репликация:** по записям holder (`NoSync`, `OwnerSync`, `PublicSync`); baker
  требует флаг синхронизации в объявлении holder `Common` и запрещает его в
  объявлении `Server`.
- **Изменяемость:** полный жизненный цикл: создание, уничтожение, события и
  временные события.
- **Идентичность:** ID сущности, а на сервере — блокировка сущности, которую
  скрипты должны покрывать.
- **Миграция:** вида правила миграции на уровне сущности нет. Правила охватывают
  `Property`, `Proto` и `Enum`, поэтому сохранённые данные сущности мигрируют
  через правила её свойств и прототипов.

## Решайте в таком порядке

1. Меняются ли данные во время игры? Если нет, это setting (один скаляр на весь
   запуск), свойство прототипа (значение по умолчанию для вида сущности) или
   строка FixedType (именованная запись, на которую ссылаются другие данные).
2. Есть ли у них собственная идентичность, события, временные события или время
   жизни, либо скриптам нужно искать их по ID и уничтожать? Делайте сущность.
   Иначе оставьте их свойствами существующей сущности.
3. Это одно значение? Используйте свойство с нужными флагами. Это несколько
   значений, которые меняются вместе и на которые никогда не ссылаются по
   отдельности? Используйте RefType. Это несколько чисел фиксированного размера,
   которые копируются? Используйте ValueType.
4. Это необязательная роль с общей проверкой наличия и несколькими связанными
   полями? Используйте компонент с неизменяемым маркером вместо параллельных
   плоских свойств.
5. Флаги сохранения и синхронизации записывайте последними и проверяйте
   перезапуск и повторное подключение на реальных объявлениях.

## Антипаттерны

| Антипаттерн | Почему это не работает | Что использовать вместо |
| --- | --- | --- |
| Setting в роли счётчика или значения отдельной сущности | Settings — стартовая конфигурация; живое состояние Engine хранит у его владельца | Изменяемое свойство сущности или сервис среды выполнения |
| Таблица строк, встроенная в список настроек или в глобальный словарь скрипта | Нет ID, проверки ссылок и миграции, отделена от bake | Каталог FixedType |
| Глобальный словарь скрипта с ключом ID сущности | Отделяет данные от времени жизни; утекает при повторном использовании ID; требует собственной очистки; становится общей границей конкурентности | Свойство сущности |
| Плоские свойства `BulletinRegion`, `BulletinStep` с наличием, выводимым из непустого поля | Нет единой проверки наличия; валидаторы и потребители гадают | Компонент с bool-маркером |
| Сущность, созданная ради простого значения | Добавляет ID, жизненный цикл, блокировку и учёт holder | Свойство или RefType |
| RefType для того, что ищут по ID, на что подписываются или что уничтожают | У RefType всего этого нет | Entity или FixedType |
| Часто меняющаяся большая коллекция внутри одного RefType | Значение читается как копия и записывается целиком | Более мелкие свойства или сущность на элемент, если нужна идентичность |
| Строки или массивы внутри ValueType | Baker их отклоняет | RefType |
| Правка раскладки ValueType на месте | Меняет раскладку байтов и версию метаданных для каждой стороны | Новый тип или свойство и миграция |
| Изменение RefType через чтение свойства | Чтение возвращает отсоединённую копию, изменение теряется | Прочитать, изменить, присвоить обратно |

## Минимальные объявления

Эти строки используют грамматику, которую проверяют тесты baker и пример
проекта. Первый блок — сторона объявления, второй — соответствующая
конфигурация.

```angelscript
namespace RepresentationSample
{

///@ Setting Server bool Starter.ExitAfterStart

///@ FixedType Server LootTable
///@ Property LootTable Server int32 Rolls

///@ Property Critter Common bool Bulletin Component
///@ Property Critter Server hstring Bulletin.Region

///@ RefType Common RouteSnapshot
///@ Property RouteSnapshot Common int32[] Steps
///@ Property RouteSnapshot Common string Note
///@ Property Critter Server RouteSnapshot Snapshot Mutable Persistent

///@ ValueType Common ThresholdPair Layout = int32 - Low + int32 - High

}
```

```ini
Starter.ExitAfterStart = False

[LootTable]
$Name = Crate
Rolls = 3
```

Первая строка `ini` — значение конфигурации, которое `MetadataBaker` требует для
setting, как это делает `Examples/MinimalProject/FOnlineStarter.fomain`;
`[LootTable]` — строка в файле-контейнере прототипов. Управляемый скрипт читает
setting как `Settings.Starter.ExitAfterStart`:

```csharp
if (Settings.Starter.ExitAfterStart)
{
    Game.RequestQuit(true);
}
```

`Examples/MinimalProject/Scripts/Starter.fos` показывает чтение той же настройки
из AngelScript. Управляемого стартового примера в Engine пока нет, поэтому этот
фрагмент C# — образец использования сгенерированного класса `Settings`, а не
проект для сборки.

## Последующее изменение представления

Перенос данных между представлениями меняет сохраняемые имена или раскладки,
поэтому относитесь к нему как к миграции:

1. Перечислите, что хранится: имена свойств, поля RefType, ID FixedType, имена
   enum и записи holder сущностей.
2. Добавьте соответствующий `MigrationRule` для каждого переименованного или
   удалённого имени и сохраняйте удалённые имена как постоянные tombstone-записи.
   Грамматику определяют [справочник по
   метаданным](../../reference/metadata/index.md#динамические-metadata) и [раздел
   о миграциях свойств документа в Managed
   C#](../../how-to/scripting/managed-csharp.md#миграция-свойств-документа).
3. Разворачивайте метаданные сервера и клиента из одного bake; несовпадение
   метаданных — дефект, а не поддерживаемый режим ([версия
   метаданных](../../reference/metadata/index.md#версия-metadata)).
4. Тестируйте на сохранении, записанном предыдущими объявлениями, и с
   перезапуском, а не только на новых данных.

## Контрольный список проверки

- [ ] Выбранное представление отвечает на вопросы: изменяемое или нет,
  сохраняется или нет, отправляется клиентам или нет, есть ли идентичность.
- [ ] Каждое объявление проходит bake без ошибок baker для ролей сервера,
  клиента и mapper.
- [ ] Постоянные данные переживают перезапуск сервера; синхронизируемые данные
  доходят до переподключающегося клиента.
- [ ] У переименованных или удалённых имён есть правила миграции и тест на
  старом сохранении.
- [ ] Ни одна глобальная карта скрипта не хранит состояние отдельных сущностей.
- [ ] Значения setting существуют в конфигурации для каждой объявленной
  настройки.
