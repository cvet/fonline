# Настройка непрерывной интеграции для игрового проекта
<!-- docs-translation: {"document_id":"project-continuous-integration","locale":"ru","source_path":"Docs/en/how-to/project/continuous-integration.md","source_sha256":"572e486c11d5268022f7f06daa02d9b96b40732e06dd6efaaa515cbde018c3f2"} -->
Руководство показывает, как встраивающий игровой проект строит непрерывную
интеграцию вокруг движка: какие линии запускать, как извлекать submodule
движка, как готовить runner командами, принадлежащими движку, как упорядочивать
jobs и ставить между ними шлюзы и как защищать секреты и доказательства. Оно
описывает паттерн; конкретные метки runners, presets, идентификаторы пакетов и
цели развёртывания принадлежат проекту.

Движок поставляет два вида доказательств CI: собственный validation workflow и
пару шаблонов workflow для публичных репозиториев с примерами. Оба служат
образцом структуры, а не готовыми release pipelines. Словарь workflow (`if:`,
`permissions`, `concurrency`, `fail-fast`, artifacts) следует GitHub Actions,
потому что именно их используют workflows движка; структура переносится и на
другие runners.

## Запускайте две линии

Проекту нужны два независимых ответа, и один workflow не может дать оба.

| Линия | Ревизия движка | Запуск | Отвечает на вопрос | Не должна |
|---|---|---|---|---|
| Pinned-Engine | Gitlink, зафиксированный в проекте | Каждый pull request и каждое обновление защищённой ветки | Корректна ли эта ревизия проекта относительно движка, с которым она поставляется? | Загружать подвижную ветку движка |
| Current-Engine | `master` движка, выбираемый после checkout | Еженедельное расписание и ручной запуск | Готово ли следующее обновление движка к принятию? | Перезаписывать gitlink, теги, сгенерированные файлы или артефакты выпуска |

Шаблоны публичных примеров реализуют ровно это разделение. Pinned-линия
проверяет контракт репозитория и точное закрепление движка перед запуском
основной проверки. Current-линия сначала проверяет то же закрепление, а затем
переключает checkout submodule:

```bash
git -C Engine fetch --depth=1 origin master
git -C Engine checkout --detach FETCH_HEAD
```

Переключение происходит после проверки закрепления, поэтому уехавший gitlink
завершается ошибкой закрепления, а не маскируется более новым checkout.
Запишите протестированный commit движка в доказательства линии. Зелёный прогон
current-линии может обосновать pull request с обновлением движка; красный
остаётся видимым и передаётся владельцу изменившейся границы. Само обновление
выполняйте по [руководству по обновлению движка](../migration/engine-upgrade.md).

Артефакты выпуска всегда происходят из pinned-линии. То же правило для реестра
примеров описано в разделе
[Линии CI](../build/public-example-repositories.md#линии-ci).

## Извлеките репозиторий

Явно извлеките проект и submodule движка и проверьте, что извлечённый движок
совпадает с зафиксированным gitlink.

```bash
git submodule update --init Engine
git submodule status Engine
git ls-tree HEAD Engine
```

`git submodule status` начинает строку с `+`, когда рабочее дерево отличается от
gitlink, и с `-`, когда submodule не инициализирован. В обоих случаях
завершайте job ошибкой.

Правила для шага checkout:

- Называйте путь движка в команде submodule. Проект, в котором есть также
  приватные или большие submodules, не должен использовать рекурсивное
  обновление без указания пути: оно загрузит репозитории, которые линии не
  нужны, и может потребовать credentials, которых у линии быть не должно.
  Шаблоны примеров используют `submodules: recursive`, потому что движок — их
  единственный submodule; копировать эту настройку в проект с другими
  submodules небезопасно.
- Репозиторий движка в этой ревизии не объявляет вложенных submodules и не
  использует Git LFS, поэтому инициализации одного `Engine` достаточно.
- Загружайте столько истории, сколько нужно проверкам. Проверкам, которые
  сравнивают с базовой ревизией, нужна полная история; собственные jobs движка
  для проверки обновлений и документации выполняют checkout с
  `fetch-depth: 0`.
- Последовательно применяйте политику окончаний строк проекта на runners
  Windows и Linux. Шаблон примера поставляет общий `.gitattributes`
  (`* text=auto eol=lf`, файлы `.cmd` и `.bat` в CRLF).
- Постоянный self-hosted runner на Windows может сохранять устаревшее написание
  каталогов после переименования, меняющего только регистр.
  `buildtools.py repair-checkout-case` выравнивает имена в рабочем дереве с
  индексом git, а его форма `--check` завершается ошибкой вместо
  переименования.

### Соблюдайте порядок для Git LFS

Движок не владеет поведением Git LFS; это общая рекомендация по Git для
проектов, которые хранят бинарные файлы в LFS, возможно на LFS-сервере,
отличном от сервера по умолчанию.

1. Выполните checkout без загрузки объектов LFS, чтобы шаг checkout не мог
   обратиться к неверному endpoint.
2. Убедитесь, что зафиксированный `.lfsconfig` (или эквивалентная настройка
   `lfs.url`) и credentials для этого сервера на месте.
3. Явно загрузите и материализуйте объекты.

```bash
export GIT_LFS_SKIP_SMUDGE=1
git checkout "$REVISION"
unset GIT_LFS_SKIP_SMUDGE
git lfs fetch origin "$REVISION"
git lfs checkout
```

`REVISION` — commit, который тестирует job. Загрузка до настройки endpoint и
credentials завершается ошибкой или обращается к неверному хосту. Перед шагом
запекания проверьте, что в дереве не осталось pointer-файлов; baker, который
читает pointer-файл, запекает мусор.

## Подготовьте runner

Используйте принадлежащие движку команды подготовки workspace из извлечённой
ревизии. Они являются версионируемым платформенным контрактом, поэтому не
копируйте в workflow список apt-пакетов или загрузку SDK.

Linux:

```bash
Engine/BuildTools/prepare-workspace.sh linux-packages
```

Windows:

```powershell
py -3 Engine\BuildTools\buildtools.py prepare-host-workspace windows
```

Оба маршрута сводятся к `buildtools.py prepare-host-workspace <host> [features]`.
Допустимые имена features перечислены в
[справочнике `prepare-host-workspace`](../../reference/buildtools/commands.md#prepare-host-workspace);
если их не указать, выбираются значения по умолчанию для хоста. Системные
пакеты (`linux-packages`, `web-packages`, `android-packages`,
`windows-cross-packages`) являются явными features и устанавливаются через apt
только на этом шаге подготовки хоста, поэтому параллельные jobs на одном хосте
не конкурируют за блокировку пакетного менеджера. Features workspace, например
`web` или `android-arm64`, пакеты не устанавливают.

Практические правила:

- Добавьте `--check`, чтобы проверить доступность без установки и сборки,
  например как preflight на self-hosted runner.
- Выбирайте расположение workspace через `FO_WORKSPACE`; по умолчанию это
  `Workspace` в текущем каталоге. Не направляйте `FO_EMSDK` на постороннее SDK;
  BuildTools выводит закреплённый путь из workspace.
- `prepare-workspace.sh`, `prepare-mac-workspace.sh` и `prepare-win-workspace.ps1`
  передают все аргументы в `buildtools.py prepare-host-workspace`, который
  отклоняет имя feature, не поддерживаемое host-системой, с кодом выхода 2 и
  перечисляет допустимые имена, поэтому опечатка или неподдерживаемая feature
  приводит к ошибке шага, а не игнорируется.
- Командная строка BuildTools — внутренний контракт (`internal`), который может
  меняться между ревизиями. Закрепите движок и читайте справочник,
  сгенерированный для этой ревизии.

Подготовку macOS оборачивает `BuildTools/prepare-mac-workspace.sh`. Для этого
руководства runners macOS не наблюдались; прежде чем заявлять линию macOS,
сверьтесь с [матрицей поддержки](../../reference/platforms/support-matrix.md).

## Используйте зеркала и кэши workspace

`prepare-host-workspace` загружает toolsets, SDK и исходники LLVM со сторонних
хостов. Проект, запускающий много jobs, может поставить перед ними собственные
хосты. Ничего не вкомпилировано; адреса передаются через окружение. Незаданная
переменная оставляет путь загрузки без изменений. Переменные описаны в разделе
[Загрузка через собственное зеркало](../build/index.md#загрузка-через-собственное-зеркало).

| Переменная | Действие |
|---|---|
| `FO_DOWNLOAD_MIRROR` | Загружает `https://host/path` как `<mirror>/host/path` |
| `FO_WORKSPACE_CACHE` | Базовый URL подготовленных workspaces (Emscripten, дерево MSVC SDK), которые собираются один раз и загружаются целиком |
| `FO_CI_TOKEN` | Bearer-токен, который отправляется только на схему и хост двух адресов выше и никогда на upstream-хост |
| `FO_CI_CA` | Путь к PEM-файлу с дополнительными якорями доверия, которые добавляются к системному хранилищу |

На что можно полагаться: загрузка сверяется с upstream `Content-Length`;
пустой, недоступный или отказывающий кэш workspace считается промахом, а не
ошибкой; повреждённый объект кэша Emscripten отбрасывается и собирается заново.
`FO_CI_CA` используется, только если путь указывает на существующий файл.

Обращайтесь с `FO_CI_TOKEN` как с секретом (см. ниже). Никогда не помещайте
keystores, credentials, состояние подписанных сессий или приватную
конфигурацию в кэш, который восстанавливают другие jobs.

## Пишите переносимые шаги

Шаги CI выполняются в разных shell на разных runners. Не держите логику в
shell.

- Предпочитайте одну команду Python на шаг. Шаг, состоящий из одного вызова
  `python <script> <arguments>`, ведёт себя одинаково на Windows, Linux и
  машине разработчика, а его код выхода является результатом шага.
- Определите интерпретатор один раз, в шаге настройки, и переиспользуйте
  результат. Обёртки движка показывают порядок: `py -3` или `python` в
  Windows, `python3`, затем `python` в остальных системах. Голый `python` на
  хосте может оказаться Python 2, а BuildTools требует Python 3.
- Избегайте возможностей shell, которые различаются между runners: цепочек
  `&&` в `cmd`, here-documents в PowerShell, `export`, раскрытия glob и
  разделителей путей. Выбирайте shell явно (`shell: bash` в каждой job,
  использующей синтаксис bash, как делает workflow движка через
  `defaults.run.shell`).
- Передавайте пути и значения аргументами, а не через встроенную интерполяцию
  недоверенного текста.
- Пусть многошаговой логикой владеет скрипт, который пишет один машиночитаемый
  результат. Скрипт можно протестировать локально, а 40-строчный блок YAML
  `run:` — нет.
- Используйте UTF-8 для любого файла с не-ASCII текстом.

## Упорядочьте jobs и задайте шлюзы

Каждая стадия отвечает на один вопрос и выполняется, только если предыдущий
ответ положительный. Дешёвые проверки идут первыми.

```text
classify changes
  -> validate / format gates          (Engine checks through project wrappers)
  -> configure + native build
  -> compile scripts                  (CompileAngelScript and/or CompileManagedScripts)
  -> bake                             (BakeResources; ForceBakeResources for release)
  -> unit tests                       (RunUnitTests)
  -> gameplay / integration           (gameplay_test_runner.py)
  -> package                          (MakePackage-<package-id>)
  -> release                          (manual, protected, preflight first)
```

| Стадия | Форма команды | Шлюз |
|---|---|---|
| Расхождение форматирования | `python Engine/BuildTools/buildtools.py format-content --check` ([Форматирование файлов игрового контента](format-content.md)) | Падает на неотформатированной главной конфигурации, файле прототипов или, с `--fos`, скрипте |
| Аудиты нативного кода | `python Engine/BuildTools/native_source_audit.py <audit> --config <file>` и `python Engine/BuildTools/native_safety_audit.py sync-scope` / `exception-safety` с `--scope`, `--config` и `--baseline` ([аудит нативного кода](native-source-audits.md), [аудит безопасности нативного кода](native-safety-audits.md)) | Текстовым аудитам нужен только Python; аудиты на основе Clang выполняются после configure и генерации кода в одной линии Clang 20 с `--require-tooling` |
| Проверки скриптов | `python Engine/BuildTools/check_script_bindings.py` и `check_angelscript_hygiene.py` с корнем, областями и baseline-файлами проекта ([проверки скриптов](script-and-binding-checks.md)) | Падает на сырых указателях на скриптовой границе, расхождении nullability обработчиков, находках гигиены модулей и устаревших строках baseline |
| Проверки контента | `python Engine/BuildTools/check_text_packs.py <roots> --config <fomain>` ([текстовые пакеты](content-and-diagnostics-tools.md#проверка-текстовых-пакетов-до-бейкинга)) и `python Engine/BuildTools/migration_guard.py --config <file> --check` ([защита миграций](migration-guard.md)) | До запекания; никогда не запускайте `--update-manifest` в CI |
| Ссылки документации | `python Engine/BuildTools/markdown_links.py --root . --exclude Engine` или обёртка проекта ([проверка документации](documentation-checks.md)) | Выполняется и для изменений только документации |
| Валидация проекта | Проверки, принадлежащие проекту, и режимы `--check` генераторов | Быстро завершается ошибкой при расхождении сгенерированных файлов и ошибках авторских данных |
| Компиляция скриптов | `cmake --build <build-dir> --config <config> --target CompileManagedScripts` (или `CompileAngelScript`) | Собирайте каждый backend скриптов, включённый проектом, для каждой роли, которую он поставляет |
| Запекание | `... --target BakeResources`; `... --target ForceBakeResources` для выпуска или при изменении графа входов | Метаданные сервера и клиента должны происходить из одного запекания |
| Unit-тесты | `... --target RunUnitTests` | Существует, если проект включает unit-тесты |
| Gameplay- и integration-тесты | `python Engine/BuildTools/gameplay_test_runner.py --manifest <manifest> --report <report>` | Готовность, обязательные и запрещённые маркеры, один дедлайн, очистка |
| Упаковка | `... --target MakePackage-<package-id>` | Только после того, как существуют бинарники и force-baked входы |
| Выпуск | Запуск, принадлежащий проекту | Только из защищённой ревизии |

Имена целей `CompileAngelScript`, `CompileManagedScripts`, `BakeResources` и
`ForceBakeResources` определяет стадия движка `ScriptsAndBaking`;
`RunUnitTests` — стадия `Applications`; имена целей пакетов задают собственные
объявления пакетов проекта. Presets и каталоги сборки принадлежат проекту,
поэтому таблица показывает формы команд, а не буквальный pipeline.
Последовательность упаковки описана в разделе
[Соберите, запеките, затем упакуйте](../release/packaging.md#соберите-запеките-затем-упакуйте),
а контракт манифеста и отчёта тестового runner — в
[Gameplay- и integration-тестировании](../testing/gameplay-and-integration.md).

Правила шлюзов:

- Используйте зависимости между jobs, чтобы поздняя стадия никогда не
  выполнялась после неудачной ранней; для матрицы платформ задайте
  `fail-fast: false`, чтобы сбой одной платформы не скрывал сбой другой.
- Никогда не совмещайте во времени запекание и потребителя его вывода в одном
  и том же каталоге вывода.
- Задайте каждой job тайм-аут. Линии примеров используют 90 минут для
  pinned-матрицы и 60 для линии совместимости.
- Отменяйте устаревшие прогоны pull request через группу concurrency, но
  никогда не отменяйте выполняющийся выпуск или прогон основной ветки. Workflow
  движка отменяет прогоны только для событий `pull_request`.
- Задайте верхнеуровневое `permissions: contents: read` и расширяйте права
  только для отдельных jobs.
- Частичное число прошедших проверок, запущенная фоновая job или пропущенная
  стадия не являются успехом. Требуйте финальный маркер успеха и код выхода.

## Пропускайте runtime-jobs для изменений только документации

Runtime-jobs (сборка, запекание, тесты, пакеты) дороги. Дешёвая job
классификации вычисляет изменённые пути относительно базовой ревизии и
публикует булевы значения, которые последующие jobs используют в своих
условиях `if:`.

- Определите группы путей один раз, в скрипте: документация, контент, скрипты,
  native-исходники, файлы сборки, файлы CI.
- Считайте, что любой путь, который скрипт не распознаёт, требует полной линии.
  Новый каталог верхнего уровня никогда не должен молча пропускать шлюз.
- Всегда запускайте полную линию в ветке по умолчанию, по расписанию и при
  запуске выпуска. Классификация только сокращает pull requests.
- Всегда запускайте validation jobs, применимые к документации (проверки
  ссылок и форматирования, см. [Проверка ссылок документации в игровом проекте](documentation-checks.md)),
  даже для изменения только документации.
- Считайте, что изменение определения CI или самого классификатора требует
  всех линий.

Собственный workflow движка не классифицирует пути; вместо этого входной
параметр `job` у `workflow_dispatch` вручную выбирает область проверки.
Паттерн классификатора принадлежит проекту.

## Сохраняйте артефакты и доказательства

Загружайте то, что нужно рецензенту для воспроизведения или диагностики
результата, а не дерево сборки.

- Называйте артефакты по проекту, линии, платформе, commit и попытке запуска,
  как делают шаблоны: `<repository>-pinned-<os>-<sha>-<run_attempt>`.
  Повторный запуск не должен перезаписывать первую попытку.
- Задайте `if-no-files-found: error`, чтобы линия, не создавшая доказательств,
  завершалась ошибкой.
- Задайте явный срок хранения. Шаблоны хранят доказательства 30 дней; движок
  хранит отчёты документации 14 дней. Выберите период, который покрывает окно
  ревью и отката проекта.
- Загружайте диагностические доказательства до более поздней и длинной стадии
  и выполняйте шаг загрузки с условием безусловного запуска, чтобы поздний сбой
  не стирал достоверные ранние доказательства, при этом job всё равно
  завершается ошибкой.
- Собирайте файлы по узкому именованному списку шаблонов. Сборщик примера
  сохраняет отчёты, снимки, манифесты пакетов и архивы выпуска и намеренно
  исключает рекурсивные копии `Build/**/Binaries`, которые дублируют
  промежуточный вывод и могут превысить тайм-аут job. Никогда не загружайте
  весь workspace.
- С каждым артефактом записывайте точный commit проекта, commit движка, хост,
  конфигурацию и результат основной проверки. Для пакетов также храните
  манифест SHA-256 и инвентарь payload, описанные в
  [Упаковке и выпуске](../release/packaging.md).
- Храните логи среды выполнения вместе с доказательствами. Имена файлов и
  поведение ротации описаны на странице
  [Файлы журналов среды выполнения и инструментов](../../reference/runtime/log-files.md).

## Защищайте секреты

Validation workflow движка служит образцом только для проверки: он не
подписывает и не развёртывает, а единственный используемый им секрет — токен
загрузки покрытия. Release-линии проекта нужны меры контроля из раздела
[Границы доверия CI](../release/security-and-secrets.md#границы-доверия-ci).
Правила, специфичные для CI:

- Недоверенный код pull request никогда не получает credentials выпуска,
  развёртывания, базы данных или подписи. Запускайте такие jobs только из
  защищённых ревизий в защищённых окружениях.
- Маскируйте секрет до того, как он попадёт в окружение. Если runner
  поддерживает маскирование, сначала зарегистрируйте маску и только затем
  экспортируйте значение в последующие шаги; значение, экспортированное до
  маскирования, уже может оказаться в логе.
- В шаге с секретами никогда не выполняйте echo или `set -x` и не печатайте
  окружение, командные строки, сгенерированную конфигурацию или ответы
  провайдера. Явно отключайте трассировку shell.
- Передавайте секрет только тому шагу, которому он нужен, как переменную
  окружения с областью этого шага, а не как аргумент командной строки и не всей
  job.
- Маскирование не является сканером: преобразованное, разделённое или короткое
  значение его обходит. Предпочитайте runtime-директивы `$TARGET_ENV`, чтобы
  секреты не попадали в запечённую конфигурацию, и сканируйте деревья пакетов
  на запрещённые файлы и синтетические canary-значения.
- Закрепляйте сторонние actions и ревизии workflow согласно политике проекта;
  считайте self-hosted runner постоянным привилегированным хостом, который
  очищается между jobs.
- Ограничивайте область `FO_CI_TOKEN` зеркалом, для которого он выполняет
  аутентификацию. Это bearer credential, и обращаться с ним нужно так же, как с
  любым другим.

## Запускайте выпуски вручную

Выпуск — это ручной запуск из защищённого ref, а не побочный эффект push.
Паттерн:

1. Входные параметры: версия или тег для публикации и флаг dry-run.
2. Preflight-job без credentials: проверьте, что входная версия совпадает с
   источником версии проекта, что тег ещё не существует, что ревизия находится
   в защищённой ветке, что gitlink движка совпадает с намеченным закреплением и
   что pinned-линия зелёная для этого commit. `release_preflight.py` выполняет
   проверки чистого дерева, версии, тега и достижимости gitlink движка и считает
   любой ref, кроме release ref, прогоном dry-run; `project_version.py --check`
   проверяет файл версии ([Инструменты выпуска для игрового проекта](release-tooling.md#выполните-предварительную-проверку-выпуска)).
   Результат pinned-линии остаётся условием workflow.
3. Соберите, запеките с `ForceBakeResources`, протестируйте и упакуйте из
   запущенного commit теми же командами, что и в pinned-линии.
4. Публикуйте, только когда флаг dry-run выключен и ref является защищённым
   release ref. На любом другом ref выполните шаги с 1 по 3 и остановитесь
   перед публикацией, чтобы правку release workflow можно было проверить в
   ветке без побочных эффектов.
5. Приложите к выпуску манифест, хеши и доказательства, затем выполните
   проверку после публикации из [Эксплуатации релиза](../release/operations.md).
   Манифест SHA-256 пишет `release_preflight.py --manifest` или
   `artifact_checksums.py` ([запись контрольных сумм пакетов](release-tooling.md#запишите-контрольные-суммы-пакетов)).

Не позволяйте release-job загружать плавающую ветку движка.

## Указывайте, что квалифицируют доказательства

- Native-сборка на одном runner не квалифицирует другую платформу, архитектуру
  или ABI. Сопоставляйте каждое утверждение с
  [матрицей поддержки](../../reference/platforms/support-matrix.md):
  compile-only, headless smoke и доказательства видимого клиента являются
  отдельными уровнями.
- Кросс-сборки и эмуляторы не являются квалификацией устройства. Headless-тест
  не является доказательством видимого клиента.
- Фикстуры упаковки движка доказывают механику пакетов, а не подпись,
  установщик, магазин, развёртывание или откат игры.
- Сообщайте о ненаблюдавшейся платформе или о развёртывании, требующем
  разрешения владельца, как об ожидающих, а не выводите успех из соседней
  линии.
- Храните доказательства точечных прогонов, полного набора, производительности,
  платформ и публикации как отдельные записи.

## Контрольный список проверки

1. Pinned-линия запускается на каждый pull request и обновление защищённой
   ветки, а current-линия запускается по расписанию и по запросу, не меняя
   gitlink.
2. Checkout инициализирует только названные submodules, проверяет gitlink
   движка и, когда используется LFS, выполняет загрузку LFS после настройки
   endpoint.
3. Подготовка runner использует команду, принадлежащую движку, а переменные
   зеркала и кэша передаются как secrets или variables, а не зашиты в код.
4. Каждый шаг — переносимая одиночная команда с явным shell и однократно
   определённым интерпретатором.
5. Jobs следуют порядку выше, с тайм-аутами, управлением concurrency и
   минимальными правами.
6. Классификатор изменений сокращает pull requests только с документацией, а
   для неизвестных путей по умолчанию требует полной линии.
7. Артефакты имеют имена с адресацией по commit, явный срок хранения и узкий
   список сбора.
8. Jobs с секретами запускаются только из защищённых ревизий; синтетическое
   canary-значение не появляется в логах, кэшах или артефактах.
9. У запуска выпуска есть preflight и dry-run на ref, не являющихся release.
10. Каждое утверждение о платформе ссылается на доказательства с этой
    платформы.
