# Чтение форматов контента движка из инструментов проекта
<!-- docs-translation: {"document_id":"project-reading-engine-formats","locale":"ru","source_path":"Docs/en/how-to/project/reading-engine-formats.md","source_sha256":"cb0f93a73fb145ea9e5927fa435182286a32b93268d23929c07493b67fd1fe64"} -->
Аудиты, линтеры и генераторы игрового проекта читают те же файлы, что и сборщики
ресурсов: главную конфигурацию, пакеты ресурсов, прототипы и текстовые пакеты.
`BuildTools/fo_formats.py` читает их так же, как парсеры движка, поэтому
инструмент проекта сообщает итоговое значение, которое дала бы сборка ресурсов,
а не догадку регулярного выражения. Используйте модуль в каждом инструменте
проекта, которому нужны значение конфигурации, входные файлы пакета,
унаследованное поле прототипа или текстовая запись, и оставляйте в проекте
только его собственную политику.

## Что читает библиотека

| Формат | Владелец в движке | Точки входа |
| --- | --- | --- |
| Грамматика конфигурации (`.fomain`, подконфигурации, любой файл с `[Section]`) | `ConfigFile.cpp` | `parse_config_text`, `read_config_file`, `parse_config_key_value_line` |
| Настройки, директивы `$ENV{}` и `$FILE{}`, `[ResourcePack]`, `[SubConfig]`, `Baking.IgnoreInputDirs` | `Settings.cpp` | `load_project_config`, `resolve_setting_value`, `ProjectConfig.setting`, `setting_list`, `setting_bool` |
| Входные файлы пакетов ресурсов | `DataSource-Directory.cpp`, `DiskFileSystem.cpp`, `FileSystem::FilterFiles` | `pack_files`, `project_files`, `match_resource_glob` |
| Секции прототипов, `$Name`, `$Parent`, `$Text` | `ProtoBaker.cpp`, `ProtoTextBaker.cpp` | `collect_prototypes`, `resolve_prototypes`, `load_project_prototypes`, `prototype_text_entries`, `decode_string` |
| Текстовые пакеты `.fotxt` и языковой fallback | `TextPack.cpp`, `TextBaker.cpp` | `parse_text_pack`, `read_text_pack`, `parse_bake_languages`, `normalize_language_packs` |
| Теги `///@` и `MigrationRule` | `MetadataBaker.cpp`, `EngineBase.cpp` | `iter_metadata_tags`, `parse_migration_rule`, `MigrationRules` |

Модуль написан на Python 3.12+ и использует только стандартную библиотеку. Он
только сообщает и никогда не пишет контент. `BuildTools/foconfig.py`, которым
пользуется упаковка, разбирает файлы той же грамматикой.

## Вывод итоговых значений из командной строки

Командная строка печатает JSON. Запускайте её из корня проекта; во встраивающем
игровом проекте движок лежит в `Engine/`.

Windows:

```powershell
py -3 Engine\BuildTools\fo_formats.py config MyGame.fomain --sub-config LocalTest --files
py -3 Engine\BuildTools\fo_formats.py protos MyGame.fomain --type Item --name Pistol
py -3 Engine\BuildTools\fo_formats.py text Texts\Dialogs.engl.fotxt
```

Linux:

```bash
python3 Engine/BuildTools/fo_formats.py config MyGame.fomain --sub-config LocalTest --files
python3 Engine/BuildTools/fo_formats.py protos MyGame.fomain --type Item --name Pistol
python3 Engine/BuildTools/fo_formats.py text Texts/Dialogs.engl.fotxt
```

В отдельном checkout движка команда
`py -3 BuildTools\fo_formats.py protos Examples\MinimalMultiplayer\FOnlineMinimalMultiplayer.fomain`
печатает прототипы примера. macOS не проверялась.

- `config` печатает настройки, которые задают файлы, после разрешения директив,
  действующие пакеты ресурсов, подконфигурации и предупреждения директив.
  `--files` добавляет входные файлы каждого пакета.
- `protos` собирает все прототипы пакетов со сборщиком ресурсов `Proto`,
  применяет объявления `MigrationRule` проекта из пакетов `Metadata` и печатает
  итоговые `properties` и `texts` для каждого `<Type> <Name>`.
- `text` печатает записи одного файла `<TextPack>.<Language>.fotxt`.

| Код выхода | Значение |
| --- | --- |
| `0` | Прочитано без замечаний. |
| `1` | `protos` или `text` нашли ввод, который сборщики ресурсов отвергают; замечания перечислены в `issues`. |
| `2` | Ошибка использования, нечитаемый файл или конфигурация, которую движок отказывается загружать. |

Полный список аргументов есть в сгенерированном
[справочнике команд помощников](../../reference/helper-cli/index.md).

## Использование из инструмента проекта

Импортируйте модуль из checkout движка. Этот аудит завершается ошибкой, если у
предмета нет итогового `Weight`, откуда бы в цепочке родителей ни приходило
значение:

```python
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]
sys.path.insert(0, str(ROOT / 'Engine' / 'BuildTools'))

import fo_formats  # noqa: E402

config = fo_formats.load_project_config(ROOT / 'MyGame.fomain')
prototypes, resolved, issues = fo_formats.load_project_prototypes(config)

for issue in issues:
    print(issue)

missing = [proto for (type_name, _), proto in sorted(resolved.items()) if type_name == 'Item' and 'Weight' not in proto.properties]

for proto in missing:
    print(f'{proto.source.path}:{proto.source.line}: item {proto.source.name} has no effective Weight')

sys.exit(1 if issues or missing else 0)
```

`ResolvedPrototype.property_sources` и `text_sources` называют прототип, чья
собственная секция дала каждое значение; это нужно аудиту «избыточного
переопределения» или «поля не на том слое». `PrototypeSource.key_lines` даёт
авторский диапазон строк каждого ключа.

## Правила, которые воспроизводит библиотека

Это крайние случаи, в которых самописные парсеры обычно расходятся со сборкой
ресурсов. Тесты привязывают каждый из них к исходнику движка или к случаю из
`Source/Tests`, откуда он взят.

Файлы конфигурации:

- `#` начинает комментарий, если он не экранирован `\` и не стоит внутри
  двойных кавычек; кавычки остаются в значении.
- `Key += value` дописывает значение через один пробел; в отсутствующий ключ
  значение записывается без ведущего пробела; пустое дописывание ничего не меняет.
- Повторный ключ заменяет прежнее значение. Повторные секции остаются
  отдельными и сохраняют порядок файла.
- Завершающий `\` после пробела или табуляции продолжает строку, в том числе на
  последней строке файла.
- Заголовок без `]` или с пустым именем игнорируется, а его ключи остаются в
  предыдущей секции.
- Метка порядка байтов (BOM) не удаляется, поэтому первая `[Section]` после неё
  не является заголовком.
- Имена секций с `/` обозначают вложенные секции; читатели прототипов
  пропускают их вместе с ключами.
- `$FILE{path}` задаётся относительно каталога объявляющей конфигурации, а его
  содержимое обрезается по краям. Неизвестная переменная `$ENV{}` или
  отсутствующий файл оставляют текст директивы и дают предупреждение.
  `$TARGET_ENV{}` и `$TARGET_FILE{}` в режиме сборки ресурсов остаются как есть.
- Значение настройки, начинающееся с `+`, дописывается к прежнему значению.
  Родители подконфигурации сливаются слева направо до собственных ключей секции.

Входные файлы пакетов ресурсов:

- Входные каталоги обходятся рекурсивно. Имена, начинающиеся с `.` или `~`, и
  каталоги, начинающиеся с `_`, пропускаются.
- Путь ресурса, присутствующий в нескольких входных каталогах одного пакета,
  берётся из первого каталога.
- `*` и `?` не выходят за один сегмент пути, `**` пересекает сегменты, а `**/`
  совпадает и с отсутствием каталога. `ExcludePatterns` сильнее `IncludePatterns`.
- Архивные входы (`InputFiles`) не открываются; `pack_files` выбрасывает
  исключение, если вызывающий код не передал `skip_archives=True`.

Прототипы:

- Тип выбирает секция: `[Proto<Type>]` или имя FixedType. Без списка FixedType
  каждая другая секция считается FixedType; передайте `fixed_types`, чтобы
  отвергать неизвестные секции, как это делает сборщик ресурсов.
- `$Name` по умолчанию равен имени файла без последнего расширения. Файл, в
  котором каждая секция задаёт `$Name`, не объявляет прототип под своим именем,
  а пустой файл не объявляет ничего.
- Имена с пробельными символами, `/` или `$` отвергаются. Идентичности и имена
  родителей проходят правила миграции `Proto`, которые следуют цепочкам
  переименований до конца, до проверки дубликатов.
- Родители применяются слева направо, каждый после своих предков, а потомок
  применяется последним, поэтому побеждает самый правый родитель. Более поздняя
  запись заменяет всё значение; списки не сливаются.
- Предок, достигнутый через двух родителей, вносит значения только там, где он
  достигнут впервые. При `Baking.AllowRepeatedProtoParents = False` это
  замечание `REPEATED_PARENT`.
- Цикл родителей, отсутствующий родитель и родитель другого типа проваливают
  прототип при любой настройке.
- Ключи `$Text [Language] [Key2] [Key3] = Value` наследуются как свойства.
  Значение декодируется: `\n`, `\"` и `\\` раскрываются, `\r` отбрасывается,
  прочие экранирования остаются буквальными, а значение, начинающееся с `"`,
  должно заканчиваться закрывающей кавычкой.

Текстовые пакеты:

- Каждая запись имеет вид `{Key1}{Key2}{Text}`. Строка без `{` пропускается;
  синтаксиса комментариев нет, поэтому комментарий с полями в фигурных скобках
  является записью.
- Только текст продолжается на следующих строках и сохраняет переводы строк,
  включая возвраты каретки файла с CRLF. Первая `}` завершает его;
  экранирования для `}` нет.
- Строка, первое поле которой не закрывается, молча пропускается. Отсутствующее
  второе поле, незакрытый текст или пустой первый ключ дают замечание, и
  сборщик ресурсов отвергает файл; корректные записи всё равно возвращаются.
- Повторные ключи являются упорядоченными вариантами. `normalize_language_packs`
  даёт языку без ключа первый вариант его fallback-языка и удаляет ключи,
  которых нет в fallback-языке.

## Ограничения

- Значения являются текстом. Типы свойств, имена enum и ссылки не проверяются;
  для этого нужны собранные метаданные.
- Типы сущностей `Proto<Type>` не сверяются с метаданными, а встроенные значения
  по умолчанию движка есть только для настроек, которые использует модуль
  (`ENGINE_SETTING_DEFAULTS`).
- Дописывание через `+` моделируется как текст, соединённый одним пробелом; так
  движок ведёт себя для строковых и списочных настроек.
- Читается только одна главная конфигурация; наслоение через `--ApplyConfig` в
  командной строке не моделируется.

## Расширение в проекте

- Держите политику проекта в модуле проекта, который импортирует `fo_formats`:
  соглашения об именах, обязательные поля по типам, соглашения о корнях
  контента, допустимые наборы языков. Библиотека отвечает на вопрос «что видит
  сборка ресурсов», модуль проекта — «приемлемо ли это для этой игры».
- Размещайте проверку проекта рядом с модулем движка, а не внутри него. Если
  проверке нужно значение, которого библиотека не отдаёт, читайте его через
  `parse_config_text` или `ResolvedPrototype`, а не разбирайте файл заново.
- Храните причину рядом с каждым исключением, которое допускает проверка
  проекта, в собственном файле исключений проекта, чтобы рецензент видел, почему
  прототип или текстовый ключ пропускается.
- Проект, который держал собственную копию парсера, переходит в три шага.
  Сначала запустите старый инструмент и библиотеку на одном дереве и сравните
  их вывод (например, итоговые свойства каждого прототипа); каждое различие —
  дефект одного из них, обычно копии. Затем замените разбор в копии импортами из
  `fo_formats` и удалите копию. Наконец, оставьте сравнение тестом проекта, пока
  проверки проекта не пройдут на одной библиотеке.
- Сообщайте о расхождении библиотеки со сборкой ресурсов как о дефекте движка с
  минимальным воспроизводящим вводом; не обходите его в проекте.

## Подключение к задачам и CI

Инструменты проекта на основе библиотеки запускаются в обычной задаче проверки
и job CI проекта до сборки ресурсов, потому что читают только исходники.
Запускайте их тем интерпретатором, который проект уже определяет для BuildTools;
см. [Пишите переносимые шаги](continuous-integration.md#пишите-переносимые-шаги).
Инструмент, который только печатает JSON (`fo_formats.py config`), относится к
диагностике, а не к шлюзу проверки.

## Контрольный список проверки

- Каждый инструмент проекта, читающий файлы `.fomain`, прототипов или `.fotxt`,
  импортирует `fo_formats` вместо собственного парсера.
- Инструмент, сообщающий значения прототипов, использует итоговые значения
  `resolve_prototypes` с `Baking.AllowRepeatedProtoParents` из главной
  конфигурации.
- Инструмент, перечисляющий контент, использует пакеты ресурсов главной
  конфигурации, а не жёстко заданный список каталогов.
- Политика проекта и исключения с причинами живут в проекте; сравнение с любой
  прежней копией парсера чистое.
- `py -3 -m pytest Engine/BuildTools/tests/test_fo_formats.py -q -p no:cacheprovider`
  проходит на ревизии движка, закреплённой проектом.
