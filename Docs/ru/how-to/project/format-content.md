# Форматирование файлов игрового контента
<!-- docs-translation: {"document_id":"project-format-content","locale":"ru","source_path":"Docs/en/how-to/project/format-content.md","source_sha256":"PLACEHOLDER"} -->
`format-content` даёт игровому проекту единую каноническую раскладку для форматов, которыми владеет движок: главного конфига `.fomain`, файлов прототипов и, по желанию, скриптов AngelScript `.fos`. Команда сортирует настройки и свойства в стабильном порядке, нормализует пустые строки и пробелы в `key = value` и перечитывает каждую переписанную конфигурацию и каждый прототип моделью читателя движка, поэтому запуск форматирования никогда не меняет то, что движок соберёт. Запускайте её перед коммитом правок контента и как CI-проверку расхождений; для собственных исходников движка на C++ и C# по-прежнему служит `format-source`.

## Что форматируется

Команда берёт область действия из главного конфига так же, как это делает сборщик ресурсов.

| Вход | Откуда берутся файлы | Раскладка |
| --- | --- | --- |
| Главный конфиг | `--fomain`, иначе единственный `*.fomain` в корне проекта | Сначала настройки главной секции без группы (ключи вида `Name`), затем по блоку на группу (`Group.Name`); группы отсортированы без учёта регистра и разделены одной пустой строкой. Внутри группы настройки идут в порядке `SETTING` из `Source/Common/Settings.inc`, затем в порядке тегов проекта `///@ Setting`; неизвестные настройки сохраняют авторский порядок после известных. Секции `[SubConfig]` начинаются с `Name` и `Parent` и используют тот же порядок без пустых строк между группами. Все остальные секции, например `[ResourcePack]`, остаются в авторском виде. |
| Файлы прототипов | Каждый `[ResourcePack]`, в `Bakers` которого есть `Proto`: каждый элемент `InputDirs` с фильтрами `IncludePatterns`/`ExcludePatterns` по грамматике шаблонов движка, за вычетом `Baking.IgnoreInputDirs`; берутся файлы с расширением из `Baking.ProtoFileExtensions` (по умолчанию в движке `fopro`) | Каждая секция `[Proto<Type>]` превращается в `$Name` и `$Parent`, затем обычные свойства в порядке объявления метаданных, затем каждый маркер компонента со своими полями, затем записи `$Text`; между этими группами одна пустая строка. Секция без `$Name` получает `$Name = <имя файла>`, то имя, которое сборщик ресурсов использует и так. |
| AngelScript | Только с `--fos <glob>` относительно корня проекта | clang-format 20 и исправление AngelScript из движка, ровно так, как их применяет wrapper в `buildtools.py`. |

Порядок свойств и настроек берётся из файлов метаданных каждого пакета ресурсов, в `Bakers` которого есть `Metadata`, отсортированных по пути внутри пакета: в этом порядке их читает `MetadataBaker`. Сложный тип, например `dict<int32, string>`, может занимать несколько токенов тега `///@ Property`. Свойства, объявленные в движке нативно, не имеют позиции в файлах метаданных и сохраняют авторский относительный порядок после свойств, объявленных в скриптах.

Эти секции остаются в авторском виде, кроме пустых строк и пробелов в конце строк:

- `[ProtoMap]` и вложенные секции вида `[<Name>/Item]`, потому что файлы карт записывает сам Mapper (`MapView::SaveToText`) и вторая раскладка спорила бы с ним;
- секции фиксированных типов, например `[QuestData]`;
- текст перед первой секцией.

Блок комментариев непосредственно над настройкой или свойством перемещается вместе с ней. Блок комментариев в конце тела секции описывает следующую секцию и переносится над её заголовок; пустая строка между блоком и заголовком сохраняется. Продолженное значение (строка, оканчивающаяся пробелом и `\`) остаётся одной записью с неизменными физическими строками.

Пример входа и выхода для прототипа с компонентом:

```ini
[ProtoItem]
$Text engl = "Rifle"
Weapon.DmgMax = 8
Weight = 5
# Shown in the barter screen
Cost = 10
Weapon = True
```

```ini
[ProtoItem]
$Name = Rifle

Weight = 5
# Shown in the barter screen
Cost = 10

Weapon = True
Weapon.DmgMax = 8

$Text engl = "Rifle"
```

## Что никогда не меняется

- Смысл. После форматирования конфига или файла прототипа инструмент разбирает исходный и полученный текст через `BuildTools/foconfig.py`, который повторяет `Source/Common/ConfigFile.cpp`: разбиение строк по LF, обрезку пробельных символов ASCII, продолжение строки после пробела или табуляции, комментарии `#` вне кавычек и экранирования, добавление через `+=` и правило «побеждает последнее присваивание». Если хоть одно имя секции, ключ или значение изменились бы, файл остаётся нетронутым, а команда завершается ошибкой. Единственное допустимое различие — добавленный `$Name`, равный имени файла.
- Детали кодировки. UTF-8 BOM сохраняется, LF или CRLF сохраняется, файл оканчивается ровно одним переводом строки.
- Порядок секций и относительный порядок повторяющихся ключей, поэтому `Key = a`, за которым следует `Key += b`, сохраняет свой результат.

Нативный читатель не удаляет BOM: BOM перед первой строкой `[ProtoItem]` скрывает этот заголовок от сборщика ресурсов. `format-content` сохраняет такой файл байт в байт и сообщает о BOM, когда переписывание изменило бы чтение первой строки. В этом случае удалите BOM вручную.

## Запуск

Из корня проекта, который встраивает движок в `Engine/`:

```powershell
py -3 Engine\BuildTools\buildtools.py format-content
py -3 Engine\BuildTools\buildtools.py format-content --check
```

```bash
python3 Engine/BuildTools/buildtools.py format-content
python3 Engine/BuildTools/buildtools.py format-content --check
```

`BuildTools/format_content.py` принимает те же параметры и может запускаться напрямую. Под `buildtools.py` корнем проекта служит `FO_PROJECT_ROOT`; если он не задан, BuildTools подставляет текущий каталог.

| Параметр | Действие |
| --- | --- |
| `--check` | Перечисляет файлы, которым нужно форматирование, ничего не записывает и завершается с кодом 1, если хоть один файл отличается. |
| `--project-root DIR` | Корень для относительных путей и поиска `*.fomain`. |
| `--fomain PATH` | Главный конфиг, который читается и форматируется. |
| `--skip-fomain` | Читать главный конфиг для области действия, но не форматировать его. |
| `--skip-protos` | Не форматировать файлы прототипов. |
| `--proto-path PATH` | Форматировать только эти файлы или каталоги вместо пакетов `Proto`; можно повторять. Файл с расширением не из `Baking.ProtoFileExtensions` считается ошибкой. |
| `--metadata PATH` | Брать порядок свойств и настроек из этих файлов в указанном порядке вместо пакетов `Metadata`; можно повторять. |
| `--fos PATTERN` | Дополнительно форматировать файлы `.fos`, подходящие под этот glob; можно повторять. |

Для `.fos` бинарный файл clang-format выбирается так же, как для `format-source`: `FO_CLANG_FORMAT`, затем `clang-format-20`, затем `clang-format` из `PATH`; он должен сообщать основную версию 20. Движок не поставляет бинарный файл. Файл стиля — собственный `.clang-format` проекта, который clang-format находит выше каждого скрипта. Полный список параметров приведён в [справочнике команд BuildTools](../../reference/buildtools/commands.md) и [справочнике вспомогательных CLI](../../reference/helper-cli/index.md).

## Коды выхода

| Код | Значение |
| --- | --- |
| `0` | Все файлы отформатированы (после записи или уже в режиме `--check`). |
| `1` | `--check` нашёл хотя бы один файл, которому нужно форматирование. Файлы перечислены как `Needs formatting: <path>`. |
| `2` | Ошибка: нет файла `*.fomain` или их несколько, отсутствует `--fomain`, неверный `--proto-path`, файл не в UTF-8, не найден clang-format 20, переписывание изменило бы смысл, или ошибка в командной строке. Для файла с ошибкой ничего не записывается. |

## Подключение к локальной задаче

Дайте проекту одну задачу, которая форматирует всё, чем он владеет, чтобы авторам не приходилось помнить порядок. Минимальная задача VS Code с выбором интерпретатора по хосту, как в [руководстве по рабочей области](vscode-workspace.md#выбор-интерпретатора-python-для-каждой-ос):

```json
{
  "label": "Format :: Content",
  "type": "process",
  "windows": {
    "command": "py",
    "args": ["-3", "Engine/BuildTools/buildtools.py", "format-content", "--fos", "Scripts/**/*.fos"]
  },
  "linux": {
    "command": "python3",
    "args": ["Engine/BuildTools/buildtools.py", "format-content", "--fos", "Scripts/**/*.fos"]
  },
  "problemMatcher": []
}
```

В проекте на Managed C# уберите аргументы `--fos`. Не запускайте форматирование, пока идёт сборка ресурсов, которая читает те же файлы.

## Добавление CI-проверки расхождений

Запускайте проверку после извлечения репозитория и до любой сборки ресурсов, чтобы ошибка форматирования стоила секунды:

```bash
python3 Engine/BuildTools/buildtools.py format-content --check
```

```powershell
py -3 Engine\BuildTools\buildtools.py format-content --check
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
```

`--check` перечисляет файлы, которым нужно форматирование, и ничего не записывает, поэтому безопасен на checkout только для чтения. Другой вариант — запустить форматирование и затем `git diff --exit-code`, как CI движка делает для `format-source`; так в журнале job виден и ожидаемый diff. Проверке `.fos` нужен clang-format 20 на runner или `FO_CLANG_FORMAT`, указывающий на закреплённый бинарный файл. Разместите job рядом с другими дешёвыми статическими проверками, описанными в [проверках качества](quality-gates.md) и [непрерывной интеграции](continuous-integration.md#упорядочьте-jobs-и-задайте-шлюзы).

## Расширение в проекте

Команда движка владеет только форматами движка. Проект держит тонкий wrapper, который вызывает её с корнями проекта, а затем запускает всё, что специфично для проекта:

```python
import subprocess
import sys
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parents[2]
CHECK = ['--check'] if '--check' in sys.argv[1:] else []

# Project-owned formatters, one command line each; every step must accept --check
PROJECT_STEPS: list[list[str]] = []


def main() -> int:
    engine = [sys.executable, str(PROJECT_ROOT / 'Engine' / 'BuildTools' / 'buildtools.py'), 'format-content', '--project-root', str(PROJECT_ROOT), *CHECK]
    codes = [subprocess.run([*engine, '--fos', 'Scripts/**/*.fos']).returncode]
    codes.extend(subprocess.run([*step, *CHECK]).returncode for step in PROJECT_STEPS)
    return max(codes)


if __name__ == '__main__':
    raise SystemExit(main())
```

Коды выхода упорядочены (`2` — ошибка, `1` — расхождение, `0` — чисто), поэтому наибольший код wrapper правильно подводит итог. Типичные шаги проекта — форматирование GUI или диалогов, проверки сгенерированных исходников и проход стиля C#.

- **Область действия.** Сужайте или расширяйте область в главном конфиге, где её читает сборщик ресурсов: `ExcludePatterns` и `Baking.IgnoreInputDirs` исключают файлы и из сборки ресурсов, и из форматирования. Для временного более узкого запуска передайте `--proto-path`.
- **Исключения с причинами.** У форматирования нет файла исключений. Файл, которому нужна ручная раскладка, должен находиться в секции, которую форматирование сохраняет как есть (фиксированный тип или файл карты), или вне пакетов `Proto`. Запишите причину комментарием `#` рядом с элементом `ExcludePatterns`; комментарии в главном конфиге остаются привязанными к настройке под ними.
- **Проверки проекта.** Аудиты контента, правила именования и проверки сгенерированных файлов выполняются в wrapper после `format-content`, каждая со своим кодом выхода; держите их вне команды движка.
- **Метаданные вне пакетов.** Если проект хранит объявления, которые не читает ни один пакет `Metadata`, передайте их через `--metadata` в нужном проекту порядке; иначе их свойства сортируются как неизвестные.

### Переход с собственной копии проекта

Проекты, которые держали собственные форматтеры `.fomain` и прототипов, переходят за один коммит:

1. Удалите проектные копии форматтеров `.fomain` и прототипов вместе с их тестами; оставьте только шаги, специфичные для проекта.
2. Направьте задачу форматирования проекта и шаг CI на `buildtools.py format-content`.
3. Один раз запустите форматирование и закоммитьте результат как чисто форматирующее изменение. Ожидайте разового diff там, где прежняя копия вела себя иначе: настройки и свойства теперь идут в порядке файлов `MetadataBaker`, настройки берутся из текущих макросов `SETTING`, раскладку получают все секции `[Proto<Type>]`, кроме `[ProtoMap]`, комментарий непосредственно над настройкой больше не получает пустую строку, а BOM сохраняется.
4. Запустите сборку ресурсов и тесты контента проекта; проверка смысла уже гарантирует одинаковое разобранное содержимое, а сборка ресурсов подтверждает область действия.

### Как были согласованы прежние копии

Прежние проектные форматтеры имели общее происхождение и разошлись. Команда движка разрешает каждое различие так:

| Поведение | Выбор движка | Причина |
| --- | --- | --- |
| Главный конфиг по умолчанию | `--fomain`, иначе единственный `*.fomain` в корне проекта | Имена проектов — параметры, а не значения по умолчанию. |
| Источник порядка настроек | Строки `SETTING(...)` в `Settings.inc` | Это текущий макрос; старые имена и старое имя include-файла не читаются. |
| Обнаружение метаданных | Только пакеты `Metadata`, отсортированные как в `MetadataBaker`; `--metadata` переопределяет | `codegen-args.txt` в дереве сборки зависит от того, какое дерево сконфигурировано; пакет — это то, что читает сборщик ресурсов. |
| Расширения метаданных | `.fos` и `.cs` | `MetadataBaker` читает оба. |
| Рекурсия во входные каталоги | Шаблоны движка: без шаблонов — каждый файл, `*` остаётся в одном каталоге, `**` пересекает каталоги | Совпадает с `FileSystem::FilterFiles`; отдельный флаг рекурсии больше не является ключом пакета ресурсов. |
| Комментарий над настройкой | Остаётся привязанным, пустая строка не вставляется | Пустые строки разделяют только группы. |
| Завершающий комментарий секции | Переносится к заголовку следующей секции | Он описывает то, что идёт дальше. |
| Неизвестный маркер компонента | Остаётся со своими полями | Неполные метаданные не должны разрывать компонент. |
| Секции прототипов с раскладкой | Каждая `[Proto<Type>]`, кроме `[ProtoMap]` | Сборщик ресурсов обрабатывает их одинаково; файлы карт принадлежат Mapper. |
| BOM | Сохраняется | Нативный читатель его не удаляет, поэтому удаление меняет то, что читает движок. |
| Продолженные строки, `+=`, `#` в кавычках | Читаются так же, как нативным читателем | Прежние копии могли их разрывать или переставлять. |
| Исправление nullable в AngelScript | Одна реализация движка в `buildtools.py` | Покрывает экземпляры шаблонов, типы funcdef, возвращаемые типы, за которыми идут квалификаторы или комментарии, и именованные аргументы, не трогая тернарные выражения. |

## Контрольный список проверки

- `python3 Engine/BuildTools/buildtools.py format-content --check` завершается с кодом 0 на чистом checkout и с кодом 1 после неотформатированной правки.
- Повторный запуск форматирования ничего не меняет.
- После первого форматирующего коммита сборка ресурсов проходит успешно, тесты контента проходят.
- CI запускает проверку до сборки ресурсов и падает при расхождении.
- Форматирование, специфичное для проекта, выполняется в wrapper проекта, а не в команде движка.
- Для AngelScript на runner есть clang-format 20, а `.clang-format` проекта закоммичен.
