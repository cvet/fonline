# Проверка ссылок документации в игровом проекте
<!-- docs-translation: {"document_id":"project-documentation-checks","locale":"ru","source_path":"Docs/en/how-to/project/documentation-checks.md","source_sha256":"580c083d802d92d7ce6c2369c8ea2c9ff39be1cb02939ea5d2c4a3ac997ac13c"} -->
Руководство показывает, как игровой проект проверяет собственный Markdown с
помощью `BuildTools/markdown_links.py` из движка: локальные ссылки должны вести к
существующим файлам, `#fragment` должен совпадать с настоящим заголовком или
HTML-якорем, файлы должны быть корректным UTF-8 со сбалансированными
ограждениями кода, а для каждой страницы можно потребовать ровно один H1.
Описаны команды, коды выхода, все параметры, тонкая обёртка проекта, подключение
к локальной задаче и CI, а также переход проекта, который держал собственную
копию такой проверки.

Движок владеет проверкой и запускает ту же логику ссылок для своей документации
через `BuildTools/docs_validate.py`. Проект владеет своей областью: какие файлы
считаются документацией, какие деревья исключены и почему, и какие правила
добавлены сверху.

## Проверенные исходные пути

- `BuildTools/markdown_links.py`
- `BuildTools/tests/test_markdown_links.py`
- `BuildTools/docs_validate.py`
- `BuildTools/docs_ai_eval.py`
- `BuildTools/docs_ai_model_eval.py`
- `BuildTools/HelperCliInterface.json`
- `.github/workflows/validate.yml`
- `Docs/en/how-to/project/quality-gates.md`
- `Docs/en/how-to/project/continuous-integration.md`
- `Docs/en/how-to/project/vscode-workspace.md`

## Что проверяется

| Проверка | Правило | По умолчанию |
|---|---|---|
| UTF-8 | Строгое декодирование; начальная метка порядка байтов допускается; символ замены U+FFFD сообщается с номером строки | Всегда |
| Ограждения | Ограждение из трёх и более обратных кавычек или тильд закрывается тем же символом, не короче открывающего и без текста после него | Всегда |
| Локальные цели | Встроенные ссылки и изображения, HTML-атрибуты `href`/`src` и определения ссылок (`[label]: path`) должны вести к существующему файлу или каталогу | Всегда |
| Граница корня | Разрешённая цель остаётся внутри `--root` или `--target-root`; символические ссылки сначала разрешаются | Всегда |
| Якоря | `#fragment` у цели `.md` или `.markdown` совпадает со slug заголовка или явным атрибутом `id`/`name` в этом файле | Всегда |
| Один H1 | Ровно один заголовок `#` вне front matter и ограждений | `--require-single-h1` |
| Метки ссылок | Для `[text][label]` и `[text][]` нужно определение `[label]:` в том же файле | `--require-reference-definitions` |

Как читаются цели:

- Цель отсчитывается от каталога документа. Цель, начинающаяся с `/`,
  отсчитывается от `--root` так же, как GitHub отображает ссылки репозитория.
- Процентное кодирование декодируется, `?query` игнорируется, `"заголовки"`
  ссылок отбрасываются, а `<угловые скобки>` позволяют пробелы в пути.
- Цель со схемой URL (`https:`, `mailto:`) или начинающаяся с `//` считается
  внешней и никогда не загружается.
- Фрагменты у целей не в Markdown (например, `Source/Game.cpp#L10`) не
  проверяются; фрагмент у каталога тоже не проверяется.
- Front matter (блок между строками `---` в начале файла), ограждённый код и
  встроенный код не считаются прозой: ссылки и заголовки внутри них
  игнорируются. Определения сносок (`[^1]: text`) не являются ссылками.

### Slug заголовков

Slug следует правилам GitHub и парсера kramdown GFM, которым пользуется GitHub
Pages: от разметки ссылки остаётся только текст, HTML-теги, обратные кавычки и
звёздочки удаляются, текст переводится в нижний регистр, удаляется всё, кроме
букв, цифр, подчёркивания, дефиса и пробела, а затем каждый пробел становится
дефисом. Пробелы не схлопываются, поэтому выпавший разделитель оставляет двойной
дефис.

| Заголовок | Фрагмент |
|---|---|
| `` ## The `verify` macro `` | `#the-verify-macro` |
| `## MCP / AiControl Validation` | `#mcp--aicontrol-validation` |
| `## GuardSystem (охрана)` | `#guardsystem-охрана` |
| второй `## Status` в файле | `#status-1` |

Фрагменты сравниваются с учётом регистра. Если заголовок должен сохранять
стабильный фрагмент при переформулировке, поставьте перед ним явный якорь,
например `<a id="inbound-hardening"></a>`.

### Ограничения

Проверка понимает ATX-заголовки и однострочные ссылки. Она не отображает
Markdown: setext-заголовки (подчёркивание `===`) не создают якорей, текст
ссылки на нескольких строках не виден, а ограждения внутри цитат не
распознаются. Порядок уровней заголовков и проза не проверяются. Вопросы
отображения решают проверки отрендеренного сайта в инструменте публикации.

## Запуск

Из корня игрового проекта, который встраивает движок в `Engine/`, сначала
выведите выбранные документы, затем проверьте их.

```powershell
py -3 Engine\BuildTools\markdown_links.py --root . --exclude Engine --exclude Build --list
py -3 Engine\BuildTools\markdown_links.py --root . --exclude Engine --exclude Build
```

```bash
python3 Engine/BuildTools/markdown_links.py --root . --exclude Engine --exclude Build --list
python3 Engine/BuildTools/markdown_links.py --root . --exclude Engine --exclude Build
```

Исключение `Engine` убирает собственные страницы движка из набора документов,
но ссылки со страниц проекта в `Engine/` по-прежнему разрешаются, и их якоря
по-прежнему проверяются. Если подмодуль не извлечён, такие ссылки падают как
отсутствующие цели, и для job документации это правильный сигнал.

Каждая находка занимает одну строку, строки отсортированы по файлу и номеру
строки, в конце идёт сводка:

```text
Docs/Combat.md:14: local link target does not exist: Weapons.md
Docs/Combat.md:31: Markdown anchor does not exist: ../Engine/Docs/en/index.md#start-here
Docs/Quests.md:5: fenced code block is never closed
Docs/World.md: expected exactly one H1 heading, found 2
markdown_links: checked 64 document(s), 4 finding(s)
```

Вывод идёт в UTF-8 даже при перенаправлении в Windows, поэтому имена файлов не
на латинице сохраняются в журналах CI.

### Коды выхода

| Код | Значение |
|---|---|
| `0` | Находок нет или `--list` завершился |
| `1` | Выведена хотя бы одна находка |
| `2` | Неверный вызов: неизвестный параметр, `--root` или `--target-root` не является каталогом, или ни один документ не подходит под шаблоны включения и исключения |

Пустой выбор падает намеренно: опечатка во включении не должна делать проверку
зелёной.

## Параметры

| Параметр | Назначение |
|---|---|
| `--root DIR` | Корень репозитория, который ограничивает цели ссылок и служит началом шаблонов; по умолчанию текущий каталог |
| `--include GLOB` | Шаблон документов, повторяемый; по умолчанию `**/*.md` и `**/*.markdown` |
| `--exclude GLOB` | Шаблон файла или каталога, убираемого из набора документов, повторяемый; совпадение с каталогом убирает всё под ним |
| `--target-root DIR` | Дополнительный каталог относительно `--root`, в который могут вести ссылки, хотя он вне корня; его файлы не проверяются как документы |
| `--skip-target GLOB` | Шаблон относительно корня для целей, которые не проверяются, для законно отсутствующего дерева, например необязательного подмодуля ассетов |
| `--allow-line-fragments` | Принимать `#L10` и `#L10-L20` у целей Markdown |
| `--require-single-h1` | Сообщать о файлах, где не ровно один H1 |
| `--h1-exempt GLOB` | Файлы, освобождённые от `--require-single-h1`, например однострочные файлы импорта инструкций |
| `--require-reference-definitions` | Сообщать о ссылках со ссылочным синтаксисом без определения метки |
| `--list` | Вывести выбранные документы и завершиться |

Шаблоны задаются относительно корня и используют `/` на любой системе: `*` и
`?` остаются внутри одного сегмента пути, `**` пересекает сегменты. `.git` никогда
не обходится, символические ссылки на каталоги не раскрываются. Сгенерированный
[справочник вспомогательных CLI](../../reference/helper-cli/commands.md) хранит
точный текст справки текущей ревизии.

Используйте `--target-root` только для дерева вне корня, например движка,
извлечённого рядом с проектом как `../Engine`. Движок, встроенный в `Engine/` как
подмодуль, уже находится внутри корня, и ему достаточно `--exclude Engine`. Если
`Engine/` является символической ссылкой или junction в Windows, его цели
разрешаются вне корня и сообщаются как выходящие за него; в такой раскладке
добавьте `--target-root Engine`.

## Обёртка в проекте

Держите область проверки в одном скрипте проекта, чтобы локальные задачи, хуки
и CI запускали одну и ту же проверку. У каждого исключения и пропущенной цели
причина записана в той же строке, поэтому рецензент видит, почему дерево вне
области.

```python
"""Check the project's Markdown links with the Engine checker."""

from __future__ import annotations

from pathlib import Path
import sys

PROJECT_ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(PROJECT_ROOT / "Engine" / "BuildTools"))

import markdown_links  # noqa: E402

EXCLUDES = [
    "Engine",  # Engine pages are checked by the Engine; links into it stay checked
    "Build",  # generated build output
    "Workspace",  # task scratch files are not maintained documentation
    "**/node_modules",  # vendored packages with upstream documentation
    "ThirdParty",  # upstream documentation keeps its own link conventions
]
SKIP_TARGETS = [
    "Art",  # optional asset submodule that documentation jobs do not check out
]
H1_EXEMPT = [
    "CLAUDE.md",  # one-line import of AGENTS.md without a heading
]


def main() -> int:
    arguments = ["--root", str(PROJECT_ROOT), "--require-single-h1"]
    for pattern in EXCLUDES:
        arguments += ["--exclude", pattern]
    for pattern in SKIP_TARGETS:
        arguments += ["--skip-target", pattern]
    for pattern in H1_EXEMPT:
        arguments += ["--h1-exempt", pattern]
    return markdown_links.main(arguments + sys.argv[1:])


if __name__ == "__main__":
    raise SystemExit(main())
```

Сохраните его как `tools/check_docs.py`. Дополнительные аргументы передаются
дальше, поэтому `py -3 tools\check_docs.py --list` (Windows) и
`python3 tools/check_docs.py --list` (Linux) показывают выбор.

### Локальная задача

Задача VS Code, запускающая обёртку, в стиле
[рекомендуемого графа задач](vscode-workspace.md#рекомендуемый-граф-задач):

```json
{
  "label": "Check :: Docs Links",
  "type": "shell",
  "windows": { "command": "py", "args": ["-3", "tools/check_docs.py"] },
  "linux": { "command": "python3", "args": ["tools/check_docs.py"] },
  "problemMatcher": []
}
```

### Запуск в CI

Запускайте обёртку в job документации на каждом pull request, включая изменения
только документации, после извлечения подмодуля движка; см.
[пропуск runtime-jobs](continuous-integration.md#пропускайте-runtime-jobs-для-изменений-только-документации).
Шаг для runner GitHub Actions на Ubuntu:

```text
- name: Check documentation links
  run: python3 tools/check_docs.py
```

Шагу нужен только Python 3.12 или новее и не нужен доступ к сети. Job должен
падать на любом ненулевом коде выхода; не добавляйте `continue-on-error`.

## Расширение в проекте

- **Область и исключения.** Меняйте только списки обёртки. Добавляйте исключение,
  когда дерево не является поддерживаемой документацией, но никогда ради того,
  чтобы скрыть битую ссылку на поддерживаемой странице. Пропущенная цель нужна
  для содержимого, которое законно отсутствует в checkout; ссылки на всё
  остальное должны разрешаться.
- **Правила проекта.** Дополнительные правила размещайте в отдельной функции
  обёртки или отдельном скрипте, который использует библиотечные функции
  `collect_documents`, `iter_links`, `resolve_local_target`, `heading_anchors` и
  `check_links`. Например, проект может запретить ссылки в свой каталог черновиков:

```python
def forbid_scratch_links(root: Path, documents: list[str]) -> list[str]:
    findings: list[str] = []
    for document in documents:
        path = root / document
        for line, target in markdown_links.iter_links(path.read_text(encoding="utf-8")):
            if markdown_links.is_external_target(target) or target.startswith("#"):
                continue
            resolved, _ = markdown_links.resolve_local_target(root, path, target)
            if resolved.is_relative_to(root / "Workspace"):
                findings.append(f"{document}:{line}: link into Workspace/: {target}")
    return findings
```

- **Особые корпуса.** Документы со своим верификатором, например копии
  доказательств, которые нужно проверять относительно закреплённой ревизии,
  остаются у этого верификатора проекта. Исключите их из общего прогона, чтобы
  у каждого файла был один владелец.
- **Более строгая структура.** Порядок уровней заголовков, стиль названий или
  правила языка проверяются рядом с обёрткой; проверка движка их не навязывает.

### Переход с собственной копии проекта

Проект, который держал собственную проверку ссылок или якорей, переходит на
проверку движка одним изменением:

1. Запишите область старого инструмента: способ поиска документов, исключённые
   каталоги, пропущенные цели, исключения для H1 и принятые формы фрагментов.
   Запустите его один раз и сохраните число документов и находки.
2. Переведите область в обёртку: исключённые каталоги становятся `--exclude`,
   никогда не извлекаемый подмодуль становится `--skip-target`, встроенный движок
   становится `--exclude Engine`, движок рядом с проектом становится
   `--target-root`, принятые фрагменты `#L10` становятся
   `--allow-line-fragments`, правило одного H1 становится `--require-single-h1` с
   записями `--h1-exempt`. Инструмент, который читал `git ls-files`, теперь
   заменён обходом дерева, поэтому явно исключите игнорируемые каталоги выходных
   файлов и кэшей.
3. Сравнивайте `tools/check_docs.py --list` со старым набором документов, пока
   они не совпадут.
4. Запустите обёртку и исправьте в документах каждую новую находку. Ожидайте
   находки, которые старая копия пропускала: теперь проверяются HTML-атрибуты
   `href`/`src` и цели в `<угловых скобках>`, цели с префиксом `/` разрешаются от
   корня, фрагменты сравниваются с учётом регистра, а slug сохраняет по дефису на
   каждый пробел (`a--b` для `A / B`).
5. Оставьте только верификаторы, специфичные для проекта, удалите старую
   проверку и её тесты и направьте локальную задачу и шаг CI на обёртку.

## Контрольный список проверки

1. `tools/check_docs.py --list` выводит поддерживаемые документы и ничего из
   исключённых деревьев.
2. Намеренно битая ссылка и намеренно неверный `#fragment` в черновой копии дают
   по одной находке и код выхода `1`.
3. Чистый прогон выводит `0 finding(s)` и завершается с `0` в Windows и Linux.
4. У каждого исключения и пропущенной цели в обёртке причина записана в её строке.
5. Job документации в CI запускает обёртку на изменениях только документации и
   падает на ненулевом коде выхода.
6. В репозитории и определениях задач не осталось копии старой проверки проекта.
