# Среда выполнения GUI

<!-- docs-translation: {"document_id":"gui-runtime-guide","locale":"ru","source_path":"Docs/en/how-to/runtime/gui.md","source_sha256":"1d53ea553567d260971073bc74504b0b679325dbed7dd267a5a04972c5b3f88a"} -->

> Документация, принадлежащая движку. Эта страница описывает переиспользуемую
> клиентскую среду выполнения GUI на AngelScript в
> `Source/Scripting/AngelScript/CoreScripts/Gui.fos` и `Input.fos`. Она не
> определяет декларативный формат файлов GUI.

## Что предоставляет Engine

FOnline предоставляет скриптовое дерево объектов, стек экранов, поведение
компоновки и отрисовки, диспетчеризацию мыши и клавиатуры, фокус, перетаскивание,
повторный ввод, сетки, представления предметов, ввод текста, окна сообщений и
консоли.

Проверяемое машиночитаемое дополнение находится в
[сгенерированном справочнике среды выполнения GUI](../../reference/gui-runtime/index.md).
Он включает все 12 типов среды выполнения, их 159 документированных членов API,
39 сигнатур callback-функций, 31 перегрузку верхнеуровневого API экранов,
встроенные аннотации метаданных и правила интеграции с этой страницы.

Engine **не** разбирает `.fogui`, `.foguischeme`, XML, JSON или другой формат
компоновки GUI. Встраиваемый проект может писать фабрики экранов AngelScript
вручную, генерировать их из принадлежащего проекту формата или использовать
отдельно версионируемый сопутствующий инструмент. Во всех случаях среда
выполнения получает классы и фабрики AngelScript, а не файлы авторинга.

## Владение исходниками

| Владелец | Поверхность |
|---|---|
| `CoreScripts/Gui.fos` | Модель объектов, экраны, компоновка, отрисовка, жизненный цикл, фокус, hit testing, drag/drop, сетки и представления предметов |
| `CoreScripts/Input.fos` | Состояние клавиш/мыши и передача нативных событий в `Gui` |
| `ClientEngine` | Нативные события ввода и разрешённая для скриптов область отрисовки `OnRenderIface` |
| Встраиваемый проект | Расширения `GuiScreen` и `CursorType`, `GuiScreens::InitializeScreens`, фабрики, вызовы lifecycle/render hooks |
| Встраиваемый проект или сопутствующий инструмент | Декларативный формат компоновки, генератор, визуальный редактор, стили, каталог экранов и проектные виджеты |

Dear ImGui является другой подсистемой. Нативные/server/tool-поверхности ImGui
и скриптовые привязки `Game.ImGui` не создают дерево экранов `Gui.fos` и не
управляют им.

## Обязательный контракт проекта

`Gui::EngineCallback_Start()` вызывает следующий внешний символ:

```angelscript
namespace GuiScreens
{
void InitializeScreens()
{
    Gui::RegisterScreen(
        GuiScreen::Login,
        GuiScreens::LoginScreen::CreateScreen);
}
}
```

Проект также должен расширить `GuiScreen` каждым зарегистрированным id:

```angelscript
///@ Enum GuiScreen Login
```

Engine объявляет только `GuiScreen::None = 0`. Аналогично, он объявляет только
`CursorType::Default = 0`; проектные режимы курсора являются метаданными
проекта.

Импорт полного каталога CoreScripts без соответствующих проектных метаданных и
реализации `GuiScreens` ожидаемо приводит к ошибке компиляции. Поэтому
минимальный серверный starter не заявлен как пример клиентского GUI.

## Мост клиентских событий

Среда выполнения реализует lifecycle- и draw-hooks, но не подписывается на все
из них автоматически. Клиентский модуль обычно связывает их так:

```angelscript
[[Event]] [[Async]]
void OnStart()
{
    // Bind fonts and perform other presentation setup first.
    Gui::EngineCallback_Start();
}

[[Event]]
void OnLoop()
{
    Gui::EngineCallback_Loop();
}

[[Event]]
void OnRenderIface()
{
    Gui::EngineCallback_Draw();
    Gui::EngineCallback_DrawCursor();
}

[[Event]]
void OnScreenSizeChanged()
{
    Gui::Callback_OnResolutionChanged();
}

void ChangeProjectLanguage(string language)
{
    Game.ChangeLanguage(language);
    Gui::Callback_OnLanguageChanged();
}
```

`EngineCallback_DrawCursor()` отделён, чтобы проект мог размещать курсор над
остальными слоями интерфейса или скрывать его для другого режима управления.

`Input.fos` работает иначе: его `[[ModuleInit]]` подписывается на
`Game.OnMouseDown`, `OnMouseUp`, `OnMouseMove`, `OnKeyDown`, `OnKeyUp` и
`OnInputLost` и передаёт их в `Gui`. Подключайте его один раз; не добавляйте
вторую копию того же моста событий.

## Модель объектов

Иерархия среды выполнения:

```text
Object
|- Panel
|  |- Screen
|  |- Grid
|  |  `- ItemView
|  `- Button
|     `- CheckBox
|        `- RadioButton
`- Text
   |- TextInput
   |  `- Console
   `- MessageBox
```

Полный список членов и сигнатур callback-функций приведён в
[сгенерированном справочнике типов](../../reference/gui-runtime/types.md).

### `Object`

`Object` владеет:

- связями родитель/потомки и рекурсивной инициализацией/удалением;
- авторскими базовыми позицией/размером и текущей абсолютной геометрией;
- состояниями active, focused, hovered, pressed, dragged и highlighted;
- значениями anchor и dock;
- политикой hit/catch/transparent-hit/focus-group;
- рекурсивными callback-функциями поиска, подсчёта, отрисовки, перемещения,
  фокуса, мыши и ввода.

Потомки рисуются в порядке массива, а hit testing выполняется в обратном
порядке. Поэтому более поздний потомок находится и визуально, и интерактивно
выше более раннего соседнего элемента.

`SetHasOnDraw(true)` обязателен, когда сгенерированный или написанный вручную
тип имеет путь `OnDraw` или `OnPostDraw`, который базовая среда выполнения не
может обнаружить самостоятельно. Без собственной причины для отрисовки или
отрисовываемого потомка `_NeedDraw` может исключить поддерево из обхода
отрисовки.

### `Panel`

`Panel` добавляет:

- фоновые спрайты и layout;
- `SetFrameImage` и отступы границ в пикселях исходника для 9-slice;
- поведение crop/scissor;
- состояние вертикальной и горизонтальной прокрутки;
- анимацию прокрутки длительностью 120 мс.

`SetBackgroundImage` может принять нативный размер спрайта, когда layout равен
`None` или у объекта нет авторского базового размера. `SetFrameImage`
намеренно сохраняет текущий размер панели, чтобы рамку можно было повторно
разбить на docked- или авторский прямоугольник.

Когда crop включён, среда выполнения применяет один и тот же прямоугольник к
отрисовке и hit testing. Потомки за его пределами не видимы и не кликабельны.

### Текст и ввод

`Text` рисует привязанным `FontType` с набором `FontFlag`, обычным и focused
цветами и значением skip-line. `SetTextWithResize` измеряет строку и изменяет
высоту; он не решает проектную политику перевода или покрытие шрифта.

`TextInput` добавляет ограничения длины, маскирование пароля, обработку
курсора/carriage, буфер обмена, включение экранной клавиатуры по фокусу и
окно показа последнего символа пароля длительностью 1000 мс.

`Console` добавляет активацию, историю, отправку и `Game.OnConsoleMessage`.
`MessageBox` поддерживает параллельные массивы текста/типа/времени, фильтрует
по `MessageBoxType` и читает `Gui.MsgboxInvert` как политику инверсии по
умолчанию.

### Кнопки и выбор

`Button` добавляет изображения/состояния pressed, hover, disabled, switched и
condition. `CheckBox` предоставляет `OnCheckedChanged`. Установленный
`RadioButton` сбрасывает switched у соседних radio-элементов одного родителя,
прежде чем вызвать собственный callback изменения.

### Сетки и представления предметов

`Grid` клонирует именованный прототип объекта в индексированные ячейки.
Прототип скрыт; `ResizeGrid` создаёт клоны, рекурсивно назначает метаданные
сетки/ячейки, вызывает callback-функции изменения размера, инициализирует клоны
и размещает их по столбцам и отступам.

`ItemView` получает клиентские handle `Item` через `OnGetItems`, отклоняет или
сортирует их через `OnCheckItem`, связывает живые предметы с ячейками и
вызывает `OnDrawItem`. Сопоставление handle намеренно отклоняет уничтоженные
handle и может заменить устаревший handle живым экземпляром с тем же id
сущности.

## Контракт компоновки

`Object::_RefreshPosition()` начинает с авторских `_BasePos` и `_BaseSize`.
Для корневых объектов текущий размер родителя равен
`Settings.View.ScreenWidth` на `Settings.View.ScreenHeight`. Для потомков это
текущий размер родителя.

### Dock

Любое значение dock, отличное от `None`, имеет приоритет над anchors:

| Dock | Позиция и размер |
|---|---|
| `Left` | Левый верхний угол родителя; сохранить ширину, заполнить высоту родителя |
| `Right` | Правый край родителя; сохранить ширину, заполнить высоту родителя |
| `Top` | Левый верхний угол родителя; заполнить ширину родителя, сохранить высоту |
| `Bottom` | Нижний край родителя; заполнить ширину родителя, сохранить высоту |
| `Fill` | Прямоугольник родителя |

### Anchor

Когда Dock равен `None`, каждая ось вычисляется отдельно:

- `Left` / `Top` сохраняет авторский отступ от соответствующего края родителя;
- `Right` / `Bottom` добавляет разницу между текущим размером и авторским
  базовым размером родителя;
- ось без подходящего edge-bit центрируется на половину этой разницы.

После изменения viewport вызовите `Gui::Callback_OnResolutionChanged()`. Он
обходит каждый зарегистрированный экран и рекурсивно пересчитывает позиции.

## Регистрация и жизненный цикл экранов

`RegisterScreen` сначала отменяет регистрацию прежнего id, игнорирует
`GuiScreen::None`, сохраняет фабрику и немедленно создаёт один экран. Первое
создание инициализирует дерево объектов и предварительно кэширует указанные
ресурсы.

Экземпляр обычного экрана остаётся зарегистрированным и переиспользуется. Для
multiinstance-экрана экземпляр прекэширования удаляется, а каждый `ShowScreen`
создаёт новый экземпляр.

`GuiScreen::Cursor` является особым: его экземпляр хранится в `CursorScreen`,
остаётся активным и исключён из обычного стека `Screens`.

### Показ

`ShowScreen` отключает направления прокрутки карты, затем:

1. переиспользует существующий не-multiinstance экран или создаёт новый;
2. заставляет предыдущий верхний активный экран исчезнуть;
3. фокусирует первое поле ввода текста и устанавливает hover;
4. перемещает показываемый экран наверх;
5. активирует его;
6. рекурсивно запускает `OnShow()` и `OnShow(params)`;
7. рекурсивно запускает `OnAppear()`;
8. вызывает `Game.OnScreenChange(true, id, params)`.

`OnShow` подходит для обновления данных. `OnAppear` означает, что экран стал
видимым верхним слоем.

### Скрытие

`HideScreen` за один вызов скрывает только один подходящий активный экземпляр:

1. запустить `OnDisappear`;
2. запустить `OnHide`;
3. деактивировать экран;
4. вызвать `Game.OnScreenChange(false, id, params)`;
5. удалить дерево multiinstance-экрана;
6. переместить следующий активный экран наверх и запустить его `OnAppear`.

`HideAllScreens` повторяет это сверху вниз, пока не останется активных экранов.

## Порядок отрисовки

Нативный `ClientEngine` разрешает скриптовую отрисовку вокруг
`Game.OnRenderIface`. Проект должен вызывать `Gui::EngineCallback_Draw()`
внутри этого события.

Проход экранов обходит `Screens` в порядке стека и рисует каждый активный
экран. Внутри отрисовываемого объекта:

1. выполняются callback-функции предмета и `OnDraw`;
2. конкретный тип рисует фон или текст объекта;
3. активные не-перетаскиваемые потомки рисуются по порядку;
4. выполняется `OnPostDraw`.

Перетаскиваемый объект пропускается в обычном поддереве и рисуется отдельным
проходом курсора. Затем рисуется необязательное меню drop, после него экран
курсора.

Отрисовка вне `OnRenderIface` не поддерживается только потому, что скриптовый
метод можно вызвать. `ClientEngine::CanDrawInScripts` ограничивает допустимую
скриптовую отрисовку.

## Ввод мышью

Mouse down начинается с верхнего активного экрана:

- очищает обычный фокус при left down;
- отменяет предыдущий press как lost;
- запускает глобальный callback экрана;
- уведомляет необязательное меню drop;
- выполняет hit testing дерева экрана;
- сохраняет и нажимает найденный объект;
- фокусирует его при left down.

Если объект не найден, левый клик закрывает экран с `IsCloseOnMiss`. Затем
немодальный экран может искать среди более низких активных экранов и вывести
вперёд первый модальный или найденный экран. Модальный экран никогда не
пропускает ввод вниз.

Mouse up выполняет global release, освобождает соответствующий pressed-объект,
создаёт click только когда указатель всё ещё попадает в него, и вызывает
drag/drop handlers в порядке регистрации, пока один из них не обработает цель.

`CheckTransparentOnHit` использует alpha спрайта для self-hit testing панели.
Он не делает произвольную геометрию потомков прозрачной.

## Клавиатура и фокус

Порядок диспетчеризации key down:

1. глобальный ввод активным экранам сверху вниз;
2. текущая консоль;
3. focused-объекты, когда активная консоль не владеет вводом.

`FocusGroup` фокусирует всё поддерево родителя вместо одного узла.
`NextTextInput` выполняет обход активного экрана в глубину.

`Input.fos` отслеживает 256 состояний клавиш и кнопки мыши до
`MouseButton::Ext4`. Он подавляет повторные события key-down, кроме `Text`,
`Space`, `Back`, `Delete`, `Left` и `Right`.

## Нажатие, перетаскивание и потеря ввода

После mouse down повтор `OnMousePressed` начинается через 500 мс и повторяется
каждые 40 мс, пока указатель всё ещё попадает в pressed-объект.

Перетаскиваемый объект переходит в drag-state после собственной пороговой
логики. При освобождении проектные handlers получают перетаскиваемый объект и
текущую hit-цель. Первый handler, вернувший `true`, получает drop.

При потере ввода `Input.fos` освобождает все отслеживаемые клавиши/кнопки.
`Gui` очищает hover, фокус и press-state, сообщает release как lost и
уведомляет меню drop. Этот контракт предотвращает залипший ввод после alt-tab,
сворачивания или потери фокуса.

Mouse down игнорируется, пока `Game.IsConnecting()`. Цикл также освобождает
состояние мыши во время подключения.

## Граница touch-ввода

`ClientEngine` создаёт отдельные события `OnTouchDown`, `OnTouchMove`,
`OnTouchUp`, tap, scroll и zoom. Стандартный GUI-мост `Input.fos` подписывается
только на события мыши, клавиатуры и потери ввода.

Не заявляйте поддержку touch на основании успешного mouse-теста. Проекту с
touch-управлением необходимо предоставить и визуально проверить собственную
адаптацию touch-to-action или touch-to-mouse.

## Подходы к авторингу

Встраиваемый проект может:

1. писать подклассы `Gui::Screen` и фабрики вручную;
2. генерировать эти классы из принадлежащего проекту декларативного источника;
3. использовать отдельно версионируемый сопутствующий GUI-пакет.

При любом подходе сгенерированный вывод должен:

- наследовать классы от точных типов среды выполнения Engine;
- использовать сигнатуры callback-функций из сгенерированного справочника;
- создавать проектные enum-метаданные и вызовы `Gui::RegisterScreen`;
- никогда не требовать от Engine чтения авторского исходника во время
  выполнения;
- быть воспроизводимым и храниться в проекте, если проектная сборка использует
  сохранённые сгенерированные скрипты.

## Диагностика

| Симптом | Первая проверка |
|---|---|
| `GuiScreen` / `GuiScreens` отсутствуют при компиляции | Проектные метаданные и `GuiScreens::InitializeScreens` |
| Экран существует, но не появляется | `RegisterScreen`, project start hook, active id, фабрика |
| Экран показывается за другим экраном | Порядок активного стека, modal-state, `BringToFront` |
| Клик приходит не тому объекту | Порядок потомков, active-state, crop-прямоугольник, transparent hit, modal fallthrough |
| UI не меняет размер | Проектный мост `OnScreenSizeChanged` и владение anchor/dock |
| Язык изменился, а текст остался прежним | `Callback_OnLanguageChanged`, `OnRefreshText`, покрытие глифов шрифта |
| `OnPostDraw` не выполняется | `SetHasOnDraw(true)` или другая причина отрисовки себя/потомка |
| Изображение drag дублируется | Обычное поддерево продолжает рисовать перетаскиваемый объект либо cursor pass вызван дважды |
| Клавиша/кнопка остаётся зажатой после потери фокуса | Дублирующий/пользовательский input bridge обходит `Input::InputLost` |
| Touch ничего не делает | Отсутствует проектная адаптация touch |

## Процесс проверки

Запустите структурные проверки Engine:

```powershell
python BuildTools\docs_gui_runtime.py --check
python -m unittest BuildTools.tests.test_docs_gui_runtime
python BuildTools\docs_validate.py
```

Затем проверьте встраиваемый проект:

1. перегенерируйте его экранный код из владеющего исходника, если он есть;
2. скомпилируйте/запеките клиент с точной ревизией Engine;
3. покажите каждый изменённый экран при минимальном, максимальном и одном
   нестандартном поддерживаемом разрешении;
4. проверьте мышь, клавиатуру, фокус, modal, close-on-miss, repeat, drag/drop и
   потерю ввода;
5. переключите каждый поставляемый язык и проверьте глифы, перенос, clipping и
   обновлённую геометрию;
6. сравните видимый результат на каждом заявленном renderer/platform;
7. проверьте логи на script exceptions, отсутствующие спрайты/шрифты и ошибки
   фабрик экранов.

Успешный headless-запуск не доказывает визуальное и интерактивное поведение. В
Engine нет самодостаточного нативного fixture, который создаёт эту среду
CoreScripts, рисует пиксели экрана, управляет вводом, меняет разрешение/язык и
доказывает teardown. Пока этот пробел не закрыт, вся поверхность остаётся
экспериментальной.

## Граница проекта

Не включайте следующие вопросы в переиспользуемую документацию Engine:

- конкретные id экранов, layout, координаты, стили и ресурсы;
- проектную грамматику наподобие `.fogui` и поведение редактора;
- сгенерированное пространство имён и пути файлов проекта;
- проектные font slots, text keys, цели доступности и политику локализации;
- игровые действия, семантику инвентаря, правила HUD и эффекты drag/drop;
- проектные screenshot baselines и отчёты приёмки платформ.

Документация Engine может определять контракт среды выполнения, который
используют эти системы. Встраиваемый проект отвечает за производство,
стилизацию и проверку своего фактического интерфейса.

## Сопровождение

Обновляйте это руководство, `BuildTools/GuiRuntimeInterface.json` и
сгенерированный справочник при изменении любого из следующих элементов:

- классов `Gui.fos`, документированных членов, callback-функций, enum,
  настроек, событий или верхнеуровневого API;
- регистрации экранов, стека, show/hide, фокуса, курсора, drag/drop, сеток,
  предметов, компоновки, crop, frame, текста, сообщений или консоли;
- подписок `Input.fos`, состояния клавиатуры/мыши, repeat, диспетчеризации или
  потери ввода;
- нативной клиентской диспетчеризации ввода или области script render;
- обязательных project hooks или внешнего контракта `GuiScreens`;
- решения о принадлежности GUI-генератора Engine, сопутствующему инструменту
  или проекту.

Перегенерируйте в порядке зависимостей:

```powershell
python BuildTools\docs_gui_runtime.py --write
python BuildTools\docs_contract_diff.py --baseline-git-ref <base> --write --enforce
python BuildTools\docs_site.py --write
python BuildTools\docs_ai_delivery.py --write
python BuildTools\docs_validate.py
```
